# React-README.md

HTML,CSS,JS 으로 훌륭한 웹 사이트를 만들었다. 근데 리액트는 왜 쓰는걸까?

- 리액트는 웹사이트의 UI(사용자 인터페이스)를 쉽고 효율적으로 만들기 위해 페이스북(Meta)이 만든 자바스크립트 '라이브러리'라고 생각하면 된다. 프레임워크가 아니라 라이브러리이기 때문에, 화면을 그리는(UI) 뼈대에 집중하고 있다.


### 본질적인 이유?
순수 자바스크립트(바닐라 JS)로 규모가 큰 웹 애플리케이션(인스타그램, 넷플릭스)을 만들 때 마주하는 3대 한계를 리액트가 해결해준다.

## 1. 레고 블록처럼 조립하는 **'컴포넌트'** 시스템
- **바닐라 JS** : 메인 페이지, 마이페이지, 상세페이지 등 매번 비슷한 헤더, 푸터, 카드 UI를 만들 때 HTML/CSS 코드를 반복 + JS로 일일이 동적 생성하면 코드가 거대해진다.
- **리액트** : 화면을 독립된 조각(컴포넌트) 단위로  쪼개서 개발한다. 레고 블록처럼 적재적소에 맞게 재사용하며, 유지보수할때도 컴포넌트 파일만 수정하니까 편리하다.

## 2. 명령형(imperative)에서 선언형(Declarative)으로의 전환
- **바닐라 JS(명령형)** : 컴퓨터에게 "1번 버튼을 누르면, 로그인 상태를 확인하고, 네비게이션 바의 클래스를 바꾸고, 프로필 이미지 태그를 찾아서 주소를 갈아 끼워라" 라고 일일이 절차를 명령해야 한다. 이는 데이터와 화면이 따로 노는 구조라 코드가 복잡해진다.
- **리액트(선언형)** : "현재 로그인 상태(State)가 true야. 그러니까 UI는 이 모습이어야 해" 라고 결과만 선언한다. 리액트가 알아서 데이터 변화를 감지하고 화면을 척척 바꿔준다. 개발자는 화면 조작 신경 안 쓰고 '데이터 관리'에만 집중할 수 있다.

#
여기서 **명령형 vs 선언형**에서의 차이점을 더 상황으로 디테일하게 파고들자면,

**바닐라 JS 방식** :
상황 : 로그인 버튼을 누름
개발자가 작성하는 코드 :
1. 로그인 상태 변수를 true로 바꿔라
2. 아이디를 가진 태그를 찾아라
3. 그 태그의 src 속성을 사용자 이미지 주소로 바꿔라
4. 네비게이션바 태그를 찾아 class에 logged-in을 추가해라

**문제점** : 화면에 요소가 100개라면, 상태가 바뀔 때마다 건드려야 할 DOM 요소가 늘어나서 코드가 엉키고 복잡해진다.

**React 방식** :
{isLoggedIn ? <UserProfileImage /> : <LoginButton />} // isLoggedIn 상태가 true면 프로필 이미지를 보여주고, false면 로그인 버튼을 보여줘"
1. 개발자는 UI가 어떻게 생겨야 하는지 상태(isLoggedIn)에 따른 모습을 미리 코드로 적어두고 상태에 따라 리액트 엔진이 이를 감지한다. 작성해둔 설계도를 보고 화면을 수정한다

**정리하면**, <UserProfileImage> 와 <LoginButton>은 각각 독립된 컴포넌트이다. 그 내부에는 각각 프로필 이미지를 렌더링하는 HTML/CSS/JS 코드(또는 JSX)가 있다.
바닐라 JS처럼 개발자가 직접 document.querySelector로 요소를 일일이 찾아서 .style을 바꾸거나 innerHTML을 갈아 끼우는 수동 작업을 할 필요가 없어진다.

개발자는 오직 "데이터(State)가 바뀌면 이 컴포넌트를 보여줘" 라고 선언만 하고, 화면의 실제 DOM 요소를 조작하고 관리하는 복잡한 일은 리액트(와 Virtual DOM)가 도맡아 처리해주기 때문에, 코드가 간결하고 유지보수하기 좋아지는 것이다.

#

## 3. 가상 DOM(Virtual DOM)을 통한 압도적인 성능과 효율
- **바닐라 JS** : 데이터가 바뀔 때마다 실제 웹페이지의 DOM(Document Object Model)을 직접 수정하면, 브라우저가 매번 화면을 다시 그리느라(Reflow/Repaint) 성능이 떨어지고 버벅일 수 있다.
- **리액트** : 메모리 상에 가짜 DOM(Virtual DOM)을 만들어두고, 데이터가 바뀔 때 진짜 화면과 가상 화면을 비교해서 바뀐 최소한의 부분만 쏙쏙 골라 한 번에 실제 브라우저에 반영한다. 속도가 빠르고 부드러운 이유이다.


사용자가 작성할 수많은 레고 블록(컴포넌트)들은 전부 ./src/ 폴더 안에 모이게 된다.
웹을 만들 때 필요한 남의 기술(라이브러리)들은 package.json에 기록되고, npm install을 통해 node_modules/에 설치되어 불러와(import) 사용된다.

## 컴포넌트의 특징

```jsx
<MyComponent user={{name: "민수"}} color="blue>
	<div>안녕하세요.</div>
<MyComponent>
```

컴포넌트에 Attribute에 해당하는 부분을 `Props`(Properties)라고 한다. -> user={{name: "민수"}} color="blue>
컴포넌트 안에 작성된 하위 Element를 children이라고 한다. 그리고 children도 결국엔 props중 하나이다.

컴포넌트끼리 데이터를 주고받을 땐 Props
컴포넌트 내에서 데이터를 관리할 땐 State
데이터는 부모 -> 자식으로만 전달



## Props란
```jsx
const Welcome = (props) => {
	return <h1>hello, {props.name}</h1>;
}
```
기본적으로 Component에 원하는 값을 넘겨줄 때 사용하며, 넘겨줄 수 있는 값은 변수, 함수, 객체, 배열 등 JavaScript의 요소라면 제한이 없다. 주로 Component의 '재사용'을 위하여 사용한다.

Props는 읽기 전용이다. 값을 임의로 변경해서 사용 x, 값을 변경해서 사용하고 싶다면, 새로운 변수를 생성


## React에서만 쓰이는 새로운 Attribute(Key)
`Key`는 React가 어떤 항목을 변경,추가 또는 삭제할지 식별하는 것을 돕는다.
Key는 엘리먼트에 안정적인 고유성을 부여하기 위해 배열 내부의 Element에 지정해야 한다.
Key는 배열 안에서 형제 사이에서 고유해야 하고 전체 범위에서 고유할 필요는 없다.



## State
`State`는 Components 내에서 유동적으로 변할 수 있는 값을 저장한다. State 값이 변경되고 재렌더링이 필요한 경우에 React가 자동으로 계산하여 변경된 부분을 렌더링한다.

State 값을 직접 변경 x -> setState 함수를 이용해 값을 변경


## 이벤트란
`이벤트(event)`란 웹 브라우저가 알려주는 HTML 요소에 대한 사건의 발생을 의미한다.
유저의 행동에 의해 발생할 수도 있으며, 개발자가 의도한 로직에 의해 발생할 수 있다.

이렇게 발생된 이벤트를 자바스크립트를 이용해 대응할 수 있다.

## 이벤트 처리(핸들링) 방법
React에서 이벤트를 처리하는 방법은 크게 두 가지 방법이 있다.
별도의 핸들링 함수를 선언하고 Element에 넘겨주는 방법 + 이벤트를 할당하는 부분에서 익명 함수를 작성하는 방법


## Hook
`Hook`이란 컴포넌트에서 데이터를 관리(State)하고 데이터가 변경될 때 상호작용(Effect)을 하기 위해 사용한다.

기존에는 컴포넌트 내에서 State와 생명주기를 관리하기 위해서 반드시 클래스 컴포넌트(Class Components)를 사용하여야 했다.

그러나 개발자가 느끼기에 다소 복잡한 클래스 컴포넌트를 보완하고 함수 컴포넌트에서 클래스 컴포넌트의 기능을 구현하기 위해 React 버전에 추가된 것이 바로 Hook 이다.


Hook은 React 함수(컴포넌트, Hook) 내에서만 사용이 가능하다.
Hook의 이름은 반드시 'use'로 시작해야 한다.
최상위 Level에서만 Hook을 호출할 수 있다.


## State Hook vs Effect Hook

State Hook

```jsx
const App = () => {
	// 일반적인 useState 사용법
	const [state 이름, setState이름] = useState(초기값)
}
```

useState는 컴포넌트 내 동적인 데이터를 관리할 수 있는 hook이다

Effect Hook
```jsx
const App = () => {
	useEffect(EffectCallback, Deps?)
}
```

EffectHook을 사용하면 함수 컴포넌트에서 side effect를 수행할 수 있다.

## 다양한 내장 Hook

- useMemo
지정한 State나 Props가 변경될 경우 해당 값을 활용해 계산된 값을 메모이제이션하여 재렌더링시 불필요한 연산을 줄인다.

- useCallback
함수를 메모이제이션 하기 위해 사용하는 Hook이다. 컴포넌트가 재렌더링될 때 불필요한 함수 생성을 방지한다.

- useRef
컴포넌트 생애 주기 내에서 유지할 ref객체를 반환한다. ref 객체는 .current라는 프로퍼티를 가지며 이 값을 자유롭게 변경할 수 있다.


## 자신만의 Hook 만들기(Custom Hook)
컴포넌트 로직을 함수로 뽑아내어 재사용할 수 있다. UI 요소의 재사용성을 올리기 위해 컴포넌트를 만드는 것 처럼, 로직의 재사용성을 높이기 위해서는 Custom Hook을 제작한다.


# React 앱에서의 스타일링 방법

1. CSS import
CSS(혹은 SCSS, Sass) 파일을 import 해서 사용, 필요한 모든 CSS 스타일을 하나의 파일에 작성하여, JS 파일과 코드 분리 가능

장단점
- 단순히 CSS 파일만을 `import`하여 사용할 수 있어 편리
- 컴포넌트가 많지 않을 경우, 하나의 CSS 파일에 코드를 관리하는 것도 가능
- CSS 파일을 분리할 수 있으나, namespace를 나눌 수 없다.
- 만일 스타일이 겹칠 경우 `cascading rule`에 따라, 마지막에 나온 룰이 덮어씌워짐


2. CSS module
- 하나의 CSS modules 파일 안에 작성한 스타일은 하나의 파일 namespace로 관리
- class name 뒤에 겹치지 않는 hash를 붙임
- 스타일이 겹치는 상황을 해결
- 두 단어 이상의 경우, class명을 camelCase로 이름을 지음


3. CSS-in-js
- 별도의 CSS 파일을 만들지 않고 하나의 컴포넌트 파일 안에서 스타일을 작성
- 자바스크립트 문법을 그대로 활용하여 코드를 작성
- React 컴포넌트를 사용하는 것처럼 사용
- Sass 문법 활용 가능

### 정리하면, 언제 어떤걸 어떻게 쓸까?

CSS import 같은 경우 공용 도화지라고 생각하면 된다.

학교 미술 시간에 모든 친구들이 거대한 대형 도화지 하나를 같이 쓰는 것이다.

내가 빨간색으로 칠해놨는데, 나중에 다른 친구가 그 자리에 파란색을 덧칠해버리면 내 그림이 파란색으려 변해버린다 -> cascading rule 충돌 -> 파일 하나로 다 같이 쓰니 처음엔 편하지만, 사람이 많아질수록(코드가 커질수록) 충돌이 많이 일어나겠지?



CSS module 같은 경우 이름표 붙은 개인 사물함 방식이라고 생각하면 된다.

내 이름표가 붙어 있는 각자의 개인 사물함을 쓰는 것이다.
내가 '내 옷' 이라고 적어두면, 리액트가 알아서 이름표 뒤에 이상한 암호(해시)를 붙여서 절대 다른 친구의 옷과 섞이지 않게 보호해 줘서 겹칠 걱정이 없다.


CSS-in-js 같은 경우 장난감 안에 색이 다 들어있는 변신 로봇 방식이라고 생각하면 된다.

물감을 따로 꺼낼 필요 없이, 장난감 블록 자체에 예쁜 색상과 스티커가 붙어서 나오는 것이다.
js 파일 하나 안에서 "너는 이 모양이고 색깔은 빨간색이야!" 하고 한 번에 코드를 작성한다. 파일을 이리저리 왔다 갔다 할 필요가 없어서 직관적이다.


웹앱을 만든다고 가정해보자,

웹사이트 전반에 걸쳐 절대 변하지 않는 기본 폰트, 전체 배경색, 초기화(Reset CSS) 같은 것들은 공용 도화지(CSS import), index.css 나 App.css 하나로 묶어서 전체에 적용하는 것이 정석이다. 협업할 때도 "이 파일은 절대 건드리지 마세요" 혹은 "기본 세팅용"이라고 약속하고 시작하는 것이다.

# Single Page Application

`SPA`은 하나의 페이지 요청으로 전체 웹앱을 사용하는 방식이다.
사용자는 웹페이지를 사용하며 모바일 앱 같은 경험을 느낀다.

Client-side routing 기술을 활용, 페이지 진입 시 리로드 없이 라우팅함.
AJAX 기술을 활용, 페이지 이동 시 서버에 데이터만 요청하여 자바스크립트로 페이지를 만듦
MPA와 다르게, 여러 페이지를 하나의 앱의 구성요소로 보고 여러 페이지 간의 스타일 컴포넌트로 재활용하는 방향으로 구현

### 장단점
- 서버에서 페이지를 만들 필요가 없으므로 CDN에 캐싱이 가능
- 매번 페이지 요청을 할 필요가 없어 네트워크 요청이 줄어듦
- 웹사이트를 개별 페이지보다는 하나의 앱으로 보는 설계로 고도의 소프트웨어 설계와 패턴을 적용할 수 있음

# Multi Page Application

`MPA`은 서버에 미리 여러 페이지를 두고, 유저가 네비게이션 시 요청에 적합한 페이지를 전달한다.
미리 서버에서 전체 페이지를 빌드해 브라우저로 전송
서버에 라우팅을 처리하는 기능이 있고, 서버에서 여러 페이지를 관리함
페이지 요청마다 모든 리소스를 다시 받아오므로, 페이지 간 데이터를 재활용하기 힘듦.




# 자바스크립트 비동기

자바스크립트는 single-threaded language이므로, 만일 서버 요청을 기다려야 한다면 유저는 멈춰있는 브라우저를 보게 될 것.

따라서 동기가 아닌 비동기 처리를 이용해 서버로 통신할 필요가 있다.

비동기 요청 후, main thread는 유저의 입력을 받거나, 페이지를 그리는 등의 작업을 처리

비동기 응답을 받으면, 응답을 처리하는 callback 함수를 task queue에 넣음

event queue는 main thread에 여유가 있을 때 task queue에서 함수를 꺼내 실행한다.

# 동기

동기 코드는, 해당 코드 블록을 실행할 때 thread의 제어권을 넘기지 않고 순서대로 실행하는 것을 의미한다.



# 스타벅스를 예시로

### 1. Promise(약속의 진동벨)

자바스크립트에서 서버에 데이터를 요청하면, 결과를 바로 받을 수 없다. 네트워크를 타고 서버다녀오는 데 시간이 걸린다.

이때 자바스크립트는 "일단 너한테 약속(Promise) 증서(진동벨)을 줄 테니까, 데이터가 준비되면 그때 줄게!"라고 말한다.

이 약속 증서가 바로 `Promise`이다.

`Promise`는 시간이 흐르면서 딱 **3가지 상태(State)**중 하나의 상태를 갖는다.

1. **Pending(대기)** : 진동벨을 받고 커피가 만들어지는 중(아직 결과가 없음)
2. **Fulfilled(이행/성공)** : 커피가 다 만들어져서 진동벨이 울림(데이터를 받아옴)
3. **Rejected(거부/실패)** : 주문이 밀려서 품절되었거나 에러가 남(데이터를 못 받아옴, 에러 발생)


과거에는 이 `Promise`가 성공했을 때와 실패했을 때를 아래처럼 `then`과 `catch` 메서드로 처리했다.


```js
getDataFromServer() 
	.then((result) => { console.log("성공", result); })
	.catch((error) => { console.log("에러 발생", error); });
```



### 2. async / await(비동기를 동기처럼)

개발자들은 `.then()` 지옥을 벗어나고자 `async`와 `await`라는 구원투수를 내놓았다.

이 문법의 본질은 간단하다. **비동기 코드인데, 마치 동기 코드(순서대로 차례)인 것처럼 눈을 속여서 편하게 작성하자!**


- `async` : 함수 앞에 붙여서 "이 함수 안에는 비동기 작업이 포함되어 있어! 라고 선언한다.
- `await` : `Promise` 앞에 붙여서 "이 작업이 끝날 때까지(진동벨이 울릴 때까지) 여기서 잠깐 멈춰(Wait) 결과 나오면 그때 다음 줄로 넘어가!" 라고 명령한다.


```js
// 1. 함수 앞에 async를 붙입니다.
async function getUserData() {
  try {
    // 2. 서버에서 데이터 가져올 때까지 await로 기다립니다! (스타벅스 진동벨 기다리기)
    const response = await fetch("https://api.example.com/user");
    
    // 3. 데이터가 다 오면 다음 코드가 실행됩니다.
    const data = await response.json();
    console.log("유저 데이터:", data);
    
  } catch (error) {
    // 4. 중간에 에러가 나면 여기서 잡아냅니다.
    console.log("데이터를 가져오는 중 에러가 발생했습니다!", error);
  }
}
```
