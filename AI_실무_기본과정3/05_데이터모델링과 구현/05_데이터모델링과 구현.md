# 데이터 모델링 - 정규화 (Normalization)

---

## 1. 이상 현상과 정규화

**이상 현상(Anomaly)** 은 잘못된 데이터베이스 설계로 인해 발생하는 오류를 의미하며, 크게 세 가지 유형으로 나눌 수 있습니다.

### 1.1 이상 현상의 유형

- **삽입 이상(Insertion Anomaly)**: 데이터를 삽입할 때 불필요한 내용까지 삽입해야 하거나, 특정 조건(예: 주문 이력)이 충족되지 않으면 데이터를 삽입할 수 없는 문제입니다.

- **갱신 이상(Update Anomaly)**: 중복된 데이터 중 일부만 갱신되어 데이터 불일치가 발생하거나, 특정 데이터를 변경할 때 모든 관련 튜플을 갱신해야 하는 문제입니다.

- **삭제 이상(Deletion Anomaly)**: 어떤 데이터를 삭제할 때 다른 유용한 정보까지 함께 삭제되는 문제입니다.

### 1.2 함수 종속성 (Functional Dependency)

**함수 종속성**은 속성들 간의 종속 관계를 나타냅니다. 어떤 속성의 한 값이 다른 속성에 속한 하나의 값에만 매핑될 때, X를 **결정자(Determinant)**, Y를 **종속자(Dependent)** 라고 합니다 (`X → Y`).

함수 종속성의 종류로는 **완전 함수 종속**, **부분 함수 종속**, **이행 함수 종속** 등이 있으며, 이를 이해해야 정규화를 통해 이상 현상을 제거할 수 있습니다.

### 1.3 정규화 (Normalization)

**정규화**는 이상 현상을 제거하고 데이터베이스를 효율적으로 구조화하는 과정입니다.

- 데이터 간의 종속성을 제거하여 중복되는 데이터를 줄입니다.
- 데이터의 **일관성(Consistency)** 과 **무결성(Integrity)** 을 보장합니다.
- 일반적으로 **1차 정규화**, **2차 정규화**, **3차 정규화**, **보이스코드 정규화(BCNF)**, **4차 정규화**, **5차 정규화** 단계가 있습니다.

### 🔍쉬운설명

이상 현상은 데이터베이스가 엉망진창이 되는 현상이라고 생각하면 됩니다. 예를 들어, 한 고객의 주소를 바꿔야 하는데 데이터베이스에 그 고객 정보가 여러 군데 흩어져 있어서 일부만 바꾸고 나머지는 안 바꾸면, 고객의 주소가 여러 개처럼 보이게 되죠. 이게 **갱신 이상**입니다.

또 다른 예로, 아직 한 번도 물건을 사지 않은 새로운 고객을 등록하려고 하는데, 고객 정보와 주문 정보를 하나의 테이블에 뭉쳐놨다면 주문 정보가 없으니 고객 정보를 아예 등록할 수 없는 경우도 생깁니다. 이게 **삽입 이상**입니다.

만약 어떤 고객이 특정 상품을 마지막으로 주문한 기록을 지웠더니, 그 고객의 이름이나 주소 같은 소중한 정보까지 몽땅 사라져 버린다면 어떨까요? 이게 바로 **삭제 이상**입니다.

이런 이상 현상들은 데이터베이스 설계가 잘못되었을 때 발생하며, 데이터를 믿고 사용하기 어렵게 만듭니다.

함수 종속성은 속성들 간의 관계를 수학적으로 표현한 것입니다. 예를 들어, 학번을 알면 이름을 알 수 있다면, 이름은 학번에 종속된다고 합니다. 이때 `학번 → 이름`으로 표시하며, 학번은 **결정자**, 이름은 **종속자**가 됩니다. 이상 현상을 해결하려면 이 종속 관계를 잘 파악해야 합니다.

정규화는 이런 이상 현상들을 없애기 위해 데이터베이스의 구조를 체계적으로 바꾸는 과정입니다. 마치 복잡하고 뒤죽박죽인 서류 더미를 깔끔하게 분류하고 정리해서, 필요한 정보를 쉽게 찾고 관리할 수 있도록 만드는 것과 같습니다. 정규화를 하면 데이터 중복이 줄어들고, 데이터가 항상 정확하고 일관되게 유지될 수 있습니다.

## 2. 1차 정규화 (1NF)

정규화를 시작하기 전에, ERD(개체-관계 다이어그램)를 한 번에 최종 형태로 설계하기보다는 지속적으로 변경하고 개선해 나가야 합니다.

**1차 정규화(1NF)** 는 테이블의 모든 컬럼이 **원자값(Atomic Value)** 을 갖도록 도메인을 설정하는 과정입니다.

- **원자값**: 더 이상 나눌 수 없는 가장 작은 값을 의미합니다.
- 예를 들어, `대여 시간` 컬럼에 여러 개의 대여 시간이 하나의 셀에 입력되어 있다면, 이를 각각의 행으로 분리하여 각 대여 시간을 독립적인 원자값으로 만듭니다.

### 🔍쉬운설명

1차 정규화는 데이터베이스 테이블의 각 칸에 데이터가 딱 하나씩만 들어가도록 만드는 과정입니다. "원자값"이라는 말이 어렵게 느껴질 수 있는데, 그냥 더 이상 쪼갤 수 없는 하나의 값이라고 생각하면 됩니다.

예를 들어, 엑셀 표에서 한 칸에 '사과, 바나나' 이렇게 여러 과일 이름을 한꺼번에 적어놓는 경우가 있죠? 1차 정규화는 이런 것을 허용하지 않습니다. '사과'는 한 칸에, '바나나'는 다른 칸에 (아니면 다른 행에) 따로 적어야 한다는 의미입니다.

강의 자료의 예시에서는 `대여 시간`이라는 칸에 `2020-08-20 13:01:02`와 `2020-09-01 20:39:52` 두 개의 대여 시간이 한꺼번에 들어가 있었습니다. 이는 원자값이 아닙니다. 1차 정규화를 통해 이 두 대여 시간을 각각의 독립적인 행으로 분리하여, 각 행의 `대여 시간` 칸에는 하나의 대여 시간만 존재하도록 만든 것입니다. 이렇게 하면 데이터를 관리하고 검색하는 것이 훨씬 쉬워집니다.

## 3. 2차 정규화 (2NF)

1차 정규화가 완료된 테이블에서 **부분 함수 종속(Partial Functional Dependency)** 을 제거하고, 모든 속성이 기본키에 대해 **완전 함수 종속(Full Functional Dependency)** 이 되도록 테이블을 분해하는 과정입니다.

- **부분 함수 종속**: 기본키가 **복합키**(두 개 이상의 속성으로 이루어진 키)일 때, 기본키를 구성하는 속성 중 일부가 결정자 역할을 하는 경우를 말합니다. 즉, 기본키의 일부만으로 다른 속성들의 값을 결정할 수 있을 때 발생합니다.
- **완전 함수 종속**: 기본키를 구성하는 모든 속성이 결정자 역할을 하는 경우입니다.

예를 들어, 복합키가 `(고객 ID, 대여 시간)`일 때, `고객 이름`은 `고객 ID`만으로 결정되므로 부분 함수 종속 관계에 있습니다. 이를 해결하기 위해 **고객 테이블**과 **대여 테이블**로 분리합니다.

### 🔍쉬운설명

2차 정규화는 '부분적인 종속 관계'를 없애는 과정입니다. 쉽게 말해, 테이블의 기본키가 여러 개의 정보로 이루어져 있을 때(복합키), 그 기본키의 일부만으로도 어떤 정보의 내용을 알 수 있다면, 그 정보들을 따로 떼어내어 새로운 테이블을 만드는 것입니다.

강의 자료의 예시를 보면, 기본키가 `(고객 ID, 대여 시간)`으로 두 개의 정보로 이루어져 있습니다. 그런데 `고객 이름`은 대여 시간과는 상관없이 오직 `고객 ID`만 알면 결정되는 정보입니다. (`고객 ID → 고객 이름`) 이런 상황에서 문제가 발생합니다.

- **삽입 이상**: 한 번도 대여하지 않은 고객은 `대여 시간` 정보가 없으므로 고객 정보를 삽입할 수 없습니다.
- **갱신 이상**: 김민준 고객의 이름을 바꾸려면 김민준이 등장하는 모든 대여 기록을 찾아 일일이 수정해야 합니다. 하나라도 빠뜨리면 데이터가 불일치하게 됩니다.
- **삭제 이상**: 이서연 고객의 willgo 킥보드 대여 기록을 삭제하면, 이서연 고객에 대한 정보가 다른 곳에 없다면 그 정보가 완전히 사라질 수 있습니다.

이런 문제들을 해결하기 위해 `고객 ID`와 `고객 이름`을 **고객 테이블**로 분리하고, 나머지 정보들을 `고객 ID(FK)`를 외래키로 사용하는 **대여 테이블**로 분리합니다. 이렇게 하면 `고객 이름`은 기본키의 '전체'가 아닌 '부분'(`고객 ID`)에만 종속되던 관계(부분 함수 종속)가 사라지게 됩니다.

## 4. 3차 정규화 (3NF)

2차 정규화가 완료된 테이블에서 **이행 함수 종속(Transitive Functional Dependency)** 을 제거하도록 테이블을 분해하는 과정입니다.

- **이행 함수 종속**: `X → Y`이고 `Y → Z`일 때, `X → Z`가 성립하는 경우를 말합니다. 즉, 기본키를 통해 직접적으로 결정되지 않고, 기본키가 아닌 다른 속성을 통해 **간접적으로** 결정되는 속성이 존재할 때 발생합니다.

예를 들어, `(고객 ID, 대여 시간)`이 기본키인 테이블에서 `(고객 ID, 대여 시간) → 브랜드명`, `브랜드명 → 회사명` 관계가 있을 때, `(고객 ID, 대여 시간) → 회사명` 관계가 성립합니다. 여기서 `회사명`은 기본키에 직접 종속되지 않고 `브랜드명`을 통해 간접적으로 종속됩니다.

이를 해결하기 위해 대여 테이블에서 `회사명`과 `분당 가격` 등의 정보를 `브랜드명`을 기본키로 하는 **회사 테이블**(또는 **가격 테이블**)로 분리합니다.

### 🔍쉬운설명

3차 정규화는 '건너뛰기 종속 관계'를 없애는 과정입니다. 어떤 정보가 기본키에 직접적으로 종속되는 것이 아니라, 기본키가 아닌 다른 중간 속성을 거쳐서 종속되는 경우를 말합니다.

강의 자료의 예시에서 `고객 ID(FK)`와 `대여 시간`이 복합 기본키인 테이블을 봅시다.

- `(고객 ID, 대여 시간)`을 알면 `브랜드명`을 알 수 있습니다. (`고객 ID, 대여 시간 → 브랜드명`)
- `브랜드명`을 알면 `회사명`을 알 수 있습니다. (`브랜드명 → 회사명`)
- 결과적으로 `(고객 ID, 대여 시간)`을 알면 `회사명`을 알 수 있게 됩니다. (`고객 ID, 대여 시간 → 회사명`)

이때 `회사명`은 기본키인 `(고객 ID, 대여 시간)`에 직접 종속되지 않고 `브랜드명`이라는 기본키가 아닌 속성을 통해 간접적으로 종속됩니다. 이것이 바로 **이행 함수 종속**입니다.

이런 상황에서 다음과 같은 이상 현상이 발생할 수 있습니다.

- **삽입 이상**: 새로운 회사가 만든 브랜드가 있는데, 아직 그 브랜드를 대여한 고객이나 대여 이력이 없다면 새로운 브랜드를 테이블에 삽입할 수 없습니다.
- **갱신 이상**: elice 회사의 boardkick 브랜드명이 변경될 경우, boardkick이라는 브랜드명을 가진 모든 대여 기록을 찾아 일일이 수정해야 합니다.
- **삭제 이상**: flykite 고객의 willgo 브랜드 대여 기록을 삭제하면, everythere 회사에 대한 정보가 다른 곳에 없다면 이 정보가 완전히 사라질 수 있습니다.

이 문제들을 해결하기 위해 `브랜드명`, `분당 가격`, `회사명`과 같은 정보를 `브랜드명`을 기본키로 하는 **회사 테이블**로 분리합니다. 또한 `브랜드명`, `연식`, `기본료`와 같은 정보를 `(브랜드명, 연식)`을 복합 기본키로 하는 **가격 테이블**로 분리할 수도 있습니다. 이렇게 테이블을 분리함으로써 이행 함수 종속을 제거하고 데이터의 독립성을 높일 수 있습니다.

## 5. 정규화 정리

정규화는 데이터베이스의 이상 현상을 제거하기 위해 여러 단계로 진행됩니다.

| 단계 | 명칭 | 제거 대상 |
|------|------|-----------|
| 비정규화 DB | — | 도메인이 원자값이 아닌 상태 |
| **1차 정규화 (1NF)** | First Normal Form | 다중값 제거 (도메인을 원자값으로 설정) |
| **2차 정규화 (2NF)** | Second Normal Form | 부분 함수 종속 제거 (기본키의 일부가 결정자 역할을 하는 경우) |
| **3차 정규화 (3NF)** | Third Normal Form | 이행 함수 종속 제거 (기본키가 아닌 속성이 다른 속성을 결정하는 경우) |
| **보이스코드 정규화 (BCNF)** | Boyce-Codd Normal Form | 결정자이면서 후보키가 아닌 것 제거 (3NF의 강화된 형태, 모든 결정자가 후보키인 상태) |
| **4차 정규화 (4NF)** | Fourth Normal Form | 다치 종속(Multi-valued Dependency) 제거 |
| **5차 정규화 (5NF)** | Fifth Normal Form | 조인 종속(Join Dependency) 제거 |

**보이스코드 정규화(BCNF) 예시**: `(학번, 과목)`이 기본키이고 `교수`가 `과목`을 결정하지만 `교수`는 후보키가 아닌 경우. (학생은 여러 과목 수강, 교수는 한 과목만 가르침)

**4차 정규화(4NF) 예시**: `(과목, 교수)`가 기본키이고, 하나의 과목에 여러 교수가 가르치고 여러 공통 교재가 사용될 때, 교수를 새로 등록하려면 교재별로 튜플을 만들어야 하여 교수가 중복 등록되는 경우.

**5차 정규화(5NF) 예시**: 하나의 수업을 여러 교수가 가르치고 학생은 같은 수업의 다른 교수 수업을 수강할 수 있을 때, 수업 테이블을 분해했다가 다시 합치면 불필요한 튜플이 발생하는 경우.

**역정규화(Denormalization)** 는 정규화된 데이터베이스의 성능을 개선하기 위해 의도적으로 다시 통합하여 구조를 재구성하는 과정입니다. 정규화를 통해 테이블을 많이 분해하면 여러 테이블을 조인해야 할 때 성능이 크게 떨어질 수 있습니다. 따라서 자주 사용되는 쿼리를 고려하여, 데이터 중복을 일부 감안하더라도 역정규화를 하는 것이 특정 상황에서는 더 효율적일 수 있습니다.

### 🔍쉬운설명

정규화 정리는 데이터베이스를 얼마나 깨끗하게 정리하느냐의 수준을 단계별로 보여주는 것입니다. 단계가 높아질수록 데이터 중복이 줄어들고 데이터의 정확성이 높아지지만, 그만큼 테이블이 많아지고 복잡해질 수 있습니다.

- **1차 정규화**는 각 칸에 딱 하나의 정보만 넣는 가장 기본적인 정리입니다.
- **2차 정규화**는 복합키의 일부만으로 결정되는 정보들을 따로 떼어내는 정리입니다.
- **3차 정규화**는 기본키가 아닌 중간 속성을 거쳐서 결정되는 정보들을 따로 떼어내는 정리입니다.
- **보이스코드 이후 정규화(BCNF, 4차 정규화, 5차 정규화)** 는 더 복잡한 종속 관계를 제거하여 데이터의 중복을 최소화하고 데이터베이스의 무결성을 극대화하는 단계입니다. 하지만 이 단계들은 실제 설계에서 항상 필요한 것은 아니며, 주로 이론적인 개념으로 다뤄지는 경우가 많습니다.

**BCNF**는 "결정자이면서 후보키가 아닌 것 제거"라는 말이 어려운데, 쉽게 말해 어떤 속성이 다른 속성들을 결정하는 능력이 있는데, 그 속성 자체가 그 테이블의 유일한 식별자가 될 수 없는 경우를 해결하는 단계입니다. (예: 교수가 과목을 결정하지만, 교수 자체가 학생-과목 테이블의 유일한 키는 아님)

**다치 종속(4NF)** 은 하나의 속성이 여러 다른 속성들과 복잡하게 얽혀서 중복이 발생하는 경우를 해결하는 것입니다. (예: 한 과목에 여러 교수가 있고 여러 교재가 있을 때, 교수를 추가하려면 교재별로 같은 교수를 계속 입력해야 하는 상황)

**조인 종속(5NF)** 은 테이블을 여러 개로 쪼갰다가 다시 합칠 때, 원래 없던 가짜 정보가 생겨나는 문제를 해결하는 것입니다.

마지막으로 **역정규화**는 이렇게 깨끗하게 정규화된 데이터베이스를 일부러 다시 합치거나 중복을 허용하는 과정입니다. 너무 테이블을 많이 쪼개 놓으면, 필요한 데이터를 가져오기 위해 여러 테이블을 계속 연결(조인)해야 하는데, 이 과정이 매우 느려질 수 있기 때문입니다. 마치 너무 깨끗하게 정리된 서류 더미에서 필요한 정보를 찾기 위해 여러 서류함을 계속 열고 닫아야 하는 것처럼요. 그래서 자주 사용하는 데이터는 약간의 중복을 감수하고 하나의 테이블에 모아두어 성능을 높이는 것이 역정규화의 목적입니다.

## 6. 공유 킥보드 DB 완성

정규화 과정을 거쳐 공유 킥보드 데이터베이스를 완성합니다. 최종 ERD는 별도 자료에 제시되어 있으며, 주요 테이블은 다음과 같습니다.

### 6.1 고객 테이블 (`customer`)

- `customer_number`를 **기본키**로 사용합니다.
- 회원 가입 시 입력받는 이름, ID, PW, 전화번호, 생년월일 등의 데이터를 포함합니다.
- 보안을 위해 **비밀번호는 해시 처리**하여 저장합니다.

### 6.2 대여 테이블 (`borrow`)

- `customer_number`와 `rental_time`을 **복합 기본키**로 사용합니다. (`customer_number`는 `customer` 테이블의 외래키)
- 대여 장소 대신 정확한 `lat_location`(위도)과 `lon_location`(경도) 데이터를 입력받습니다.
- `rental_status`는 `ENUM('대여', '반납')`으로 대여 상태를 기록합니다.
- `kickboard_id`를 **외래키**로 사용하여 `kickboard` 테이블과 연결합니다.

### 6.3 킥보드 테이블 (`kickboard`)

- `id`를 **기본키**로 사용합니다.
- `brand_number`를 **외래키**로 사용하여 `brand` 테이블과 연결합니다.
- `model_year`, `price_per_minute`, `basic_price` 등의 킥보드 관련 정보를 포함합니다.
- 가격을 계산하는 쿼리가 많아 `분당 가격` 컬럼을 이 테이블에 직접 포함시켜 성능을 향상시켰습니다 (**역정규화**의 일환). 기본료나 분당 가격이 변경되는 경우가 적기 때문에 데이터 불일치 위험을 감수합니다.

### 6.4 브랜드 테이블 (`brand`)

- `brand_number`를 **기본키**로 사용합니다.
- `name`(브랜드 이름)과 `company`(회사) 정보를 포함합니다.
- 킥보드가 없더라도 새로운 브랜드를 등록할 수 있도록 분리하였습니다 (**삽입 이상 제거**).

### 🔍쉬운설명

공유 킥보드 DB 완성 부분은 지금까지 배운 정규화 개념을 바탕으로 실제 데이터베이스를 어떻게 설계하는지 보여주는 실전 예시입니다.

우리가 처음에 봤던 복잡하고 중복 많던 하나의 큰 테이블을 정규화 과정을 거쳐 4개의 작은 테이블로 나누고 각각의 역할을 명확히 한 것입니다.

- **고객 테이블**: 고객 개인의 정보(누구인지, 연락처, 생년월일 등)만 모아 놓은 곳입니다. 여기서 중요한 건 고객을 식별하는 고유한 `고객 번호`를 기본키로 사용하고, 비밀번호는 보안을 위해 해시 처리한다는 점입니다.

- **대여 테이블**: 어떤 고객이 언제, 어디서, 어떤 킥보드를 대여했는지에 대한 기록을 모아 놓은 곳입니다. 여기서는 대여 장소를 단순히 '강남구 역삼동' 대신 **위도**와 **경도**처럼 더 정확한 위치 정보로 저장하고, 대여와 반납 상태를 기록합니다. `고객 번호`와 `킥보드 ID`가 다른 테이블에서 온 외래키로 사용됩니다.

- **킥보드 테이블**: 각각의 킥보드(`id`)에 대한 고유 정보(어떤 브랜드인지, 몇 년식인지, 분당 가격, 기본료 등)를 모아 놓은 곳입니다. 여기서 눈여겨볼 점은 **분당 가격**과 **기본료**를 이 테이블에 직접 넣어 두었다는 것입니다. 원래는 3차 정규화에 따라 이 정보를 브랜드 테이블이나 가격 정책 테이블로 분리할 수도 있지만, 가격 계산 쿼리가 자주 사용될 것을 고려하여 성능을 위해 약간의 중복을 감수하고 여기에 배치한 것입니다. 이것이 바로 **역정규화**의 실제 적용 사례입니다.

- **브랜드 테이블**: 킥보드 브랜드에 대한 정보(브랜드 이름, 제조 회사)만 모아 놓은 곳입니다. `브랜드 번호`를 기본키로 사용하여, 아직 어떤 킥보드도 출시되지 않은 새로운 브랜드라도 미리 등록할 수 있도록 **삽입 이상**을 해결했습니다.

이렇게 여러 테이블로 나누고 서로 외래키로 연결하면, 데이터 중복이 줄어들고, 데이터가 훨씬 정확하고 효율적으로 관리될 수 있습니다. 각 테이블이 하나의 명확한 주제만 다루기 때문에 수정이나 삭제도 훨씬 안전해집니다.

## 1. MySQL 설치 (윈도우)

윈도우 환경에서 MySQL을 설치하는 방법은 크게 두 가지입니다.

첫째는 MySQL 공식 문서에서 제공하는 **인스톨러**를 사용하는 것이고, 둘째는 **Chocolatey**와 같은 윈도우용 패키지 매니저를 이용하는 것입니다.

Chocolatey를 이용한 설치 방법:

1. `PowerShell`을 **관리자 권한**으로 실행합니다.
2. Chocolatey 설치 명령어를 실행합니다.
3. `choco install mysql` 명령어로 MySQL을 설치합니다.
4. 설치 중 스크립트 실행 여부를 묻는 메시지가 나오면 `a`를 입력하여 모두 허용합니다.
5. 쉘 재접속 후 `mysql --version` 명령어로 설치를 확인합니다.

### 🔍쉬운설명

윈도우 컴퓨터에 MySQL 데이터베이스를 설치하는 방법은 두 가지가 있어요. 첫 번째는 MySQL 공식 웹사이트에서 설치 프로그램을 다운받아 실행하는 것이고, 두 번째는 **Chocolatey**라는 프로그램을 사용해서 간단하게 설치하는 방법이에요.

Chocolatey로 설치하려면, 먼저 컴퓨터의 `PowerShell`이라는 프로그램을 관리자 권한으로 열어야 해요. 마치 컴퓨터의 관리자 모드로 들어가는 것과 같아요. 그 다음 Chocolatey 설치 명령어를 복사해서 `PowerShell`에 붙여넣고 실행하면 Chocolatey가 설치돼요.

Chocolatey가 설치되면 `choco install mysql`이라는 명령어를 입력해서 MySQL을 설치할 수 있어요. 설치 중에 '이 스크립트를 실행할까요?'라고 물으면 `a`를 눌러서 '모두 허용'하면 됩니다. 설치가 끝나면 `PowerShell`을 껐다가 다시 켜서 `mysql --version`이라는 명령어를 입력해보면 MySQL이 제대로 설치되었는지 확인할 수 있습니다.

## 2. MySQL 서버 실행 및 접속 (윈도우)

MySQL 서버를 실행하기 위해서는 명령 프롬프트를 **관리자 권한**으로 실행한 후 `net start mysql` 명령어를 입력합니다.

MySQL에 접속하려면 `mysql -u root -p` 명령어를 입력하고, 초기 비밀번호는 설정되어 있지 않으므로 엔터를 눌러 접속하거나 `-p` 옵션 없이 접속할 수 있습니다.

- 접속 종료: `\q`
- 서버 종료: `net stop mysql`

### 🔍쉬운설명

MySQL을 사용하려면 먼저 MySQL 서버를 켜야 해요. 윈도우에서는 '명령 프롬프트'를 관리자 권한으로 열고 `net start mysql`이라고 입력하면 서버가 시작됩니다.

서버가 켜지면 데이터베이스에 접속해야 하는데, 이때 `mysql -u root -p`라고 입력해요. `root`는 관리자 계정 이름이고, `-p`는 비밀번호를 입력하겠다는 의미예요. 처음에는 비밀번호가 설정되어 있지 않으니 그냥 엔터를 누르면 접속될 거예요.

접속을 끝내고 싶을 때는 `\q`라고 입력하고, 아예 MySQL 서버를 끄고 싶을 때는 `net stop mysql`이라고 입력하면 됩니다.

## 3. MySQL 설치 (맥)

맥 환경에서는 주로 **Homebrew**를 이용하여 MySQL을 설치합니다.

1. [https://brew.sh/index_ko](https://brew.sh/index_ko) 에서 Homebrew 설치 명령어를 복사하여 터미널에 붙여넣어 실행합니다.
2. Homebrew가 설치된 후에는 `brew install mysql` 명령어를 사용하여 MySQL을 설치합니다.

### 🔍쉬운설명

맥 컴퓨터에 MySQL을 설치하려면 **Homebrew**라는 패키지 관리 도구를 사용하는 것이 일반적이에요. Homebrew는 맥에서 소프트웨어를 쉽게 설치하고 관리할 수 있게 해주는 프로그램입니다.

Homebrew 웹사이트에 가서 설치 명령어를 복사한 다음, 맥의 '터미널'이라는 프로그램을 열어서 그 명령어를 붙여넣고 실행하면 Homebrew가 설치됩니다. Homebrew가 설치된 후에는 터미널에 `brew install mysql`이라고 입력하기만 하면 MySQL이 자동으로 설치됩니다.

## 4. MySQL 서버 실행 및 접속 (맥)

맥에서 MySQL 서버를 실행하려면 `mysql.server start` 명령어를 사용합니다.

MySQL에 접속하려면 `mysql -u root` 명령어를 사용합니다.

- 접속 종료: `\q`
- 서버 종료: `mysql.server stop`

### 🔍쉬운설명

맥에서 MySQL 서버를 켜려면 `mysql.server start`라는 명령어를 터미널에 입력하면 돼요. 서버가 켜지면 `mysql -u root`라고 입력해서 데이터베이스에 접속할 수 있습니다. 윈도우와 달리 맥에서는 `-p` 옵션 없이 바로 접속할 수 있어요(초기 비밀번호가 없는 경우). 작업을 마친 후 접속을 끊으려면 `\q`를 입력하고, 서버를 완전히 끄려면 `mysql.server stop`이라고 입력합니다.

## 5. 데이터베이스 생성

테이블을 담을 데이터베이스를 생성할 때는 `CREATE DATABASE 데이터베이스명;` 명령어를 사용합니다.

```sql
-- 데이터베이스 생성
CREATE DATABASE shared_kickboard;

-- 데이터베이스 목록 확인
SHOW DATABASES;

-- 특정 데이터베이스 선택 및 사용
USE 데이터베이스명;

-- 데이터베이스 삭제
DROP DATABASE 데이터베이스명;
```

`USE 데이터베이스명;` 명령어 이후부터는 해당 데이터베이스 내에서 테이블을 정의하거나 데이터를 조작할 수 있습니다.

### 🔍쉬운설명

데이터베이스를 만들 때는 `CREATE DATABASE`라는 명령어를 쓰고 뒤에 만들고 싶은 데이터베이스 이름을 붙여주면 돼요. 예를 들어, `shared_kickboard`라는 데이터베이스를 만들고 싶으면 `CREATE DATABASE shared_kickboard;`라고 입력하면 됩니다.

잘 만들어졌는지 확인하고 싶으면 `SHOW DATABASES;`라는 명령어를 입력해서 현재 있는 모든 데이터베이스 목록을 볼 수 있어요. 특정 데이터베이스 안에서 작업을 하고 싶을 때는 `USE 데이터베이스명;`이라고 입력해요. 그러면 그 데이터베이스 안으로 들어가는 것과 같아서 그 안에 테이블을 만들거나 데이터를 바꾸는 등의 작업을 할 수 있습니다. 더 이상 필요 없는 데이터베이스는 `DROP DATABASE 데이터베이스명;` 명령어로 지울 수 있습니다.

## 6. 데이터 제어어 (DCL)

**DCL(Data Control Language)** 은 데이터베이스에 접근하는 권한을 관리하는 등의 데이터 제어에 사용됩니다. 주요 명령어는 다음과 같습니다.

- **`GRANT`**: 데이터베이스 권한 부여
- **`REVOKE`**: 데이터베이스 권한 회수

이외에도 트랜잭션 작업을 제어하는 **`COMMIT`**(트랜잭션 작업을 반영하여 저장)과 **`ROLLBACK`**(트랜잭션 작업을 취소하여 이전 상태로 돌림) 명령어도 있으며, 이들은 종종 **TCL(Transaction Control Language)** 로 분류되기도 합니다.

### 🔍쉬운설명

DCL은 데이터베이스를 안전하게 관리하기 위한 '보안 관리' 명령어라고 생각하면 돼요. 누가 어떤 데이터를 보고, 수정하고, 삭제할 수 있는지 등의 권한을 주는 역할을 합니다.

- **`GRANT`**: 특정 사용자에게 데이터베이스를 사용할 수 있는 권한을 '부여'하는 명령입니다. 예를 들어, 어떤 학생에게 성적표를 볼 수 있는 권한을 주는 것과 같아요.
- **`REVOKE`**: 부여했던 권한을 '회수'하는 명령입니다. 위 예시에서 학생의 성적표 조회 권한을 다시 뺏는 것과 같습니다.

`COMMIT`과 `ROLLBACK`은 데이터베이스 변경 사항을 처리하는 명령이에요.

- **`COMMIT`**: 변경된 내용을 데이터베이스에 '최종 반영'하여 저장하는 것을 의미해요. 마치 문서 작업을 마치고 '저장' 버튼을 누르는 것과 같아요.
- **`ROLLBACK`**: 변경된 내용을 '취소'하고 이전 상태로 되돌리는 것을 의미해요. 문서 작업을 하다가 실수해서 '실행 취소'하는 것과 비슷합니다.

이 두 명령어는 **트랜잭션**이라는, 데이터베이스에서 하나의 논리적인 작업 단위를 제어하는 데 사용되며, DCL과 구분하여 **TCL(Transaction Control Language)** 이라고 부르기도 합니다.

## 7. 사용자 생성 및 권한 부여

새로운 사용자를 생성할 때는 다음 명령어를 사용합니다.

```sql
CREATE USER 유저이름@localhost IDENTIFIED BY '비밀번호';
```

여기서 `localhost`는 로컬 호스트(자신의 컴퓨터)에서의 접속만 허용한다는 의미이며, 외부 접속을 허용하려면 `'%'`를 사용합니다.

생성된 사용자에게 권한을 부여할 때는 다음 명령어를 사용합니다.

```sql
GRANT ALL PRIVILEGES ON 데이터베이스명.테이블명 TO 유저이름@localhost;
```

`ALL`은 모든 권한(`SELECT`, `INSERT`, `DELETE` 등)을 의미하며, 특정 권한만 부여할 수도 있습니다. 권한 설정 후에는 **`FLUSH PRIVILEGES;`** 명령어로 권한 설정을 적용해야 합니다.

```sql
-- 부여된 권한 확인
SHOW GRANTS FOR 유저이름@localhost;

-- 권한 제거
REVOKE ALL ON 데이터베이스명.테이블명 FROM 유저이름@localhost;
```

### 🔍쉬운설명

데이터베이스를 여러 사람이 사용하거나, 특정 프로그램이 사용하게 하려면 각자 다른 계정을 만들어주고 그 계정에 맞는 권한을 줘야 해요.

- **사용자 만들기**: `CREATE USER` 명령어로 새로운 계정을 만들 수 있어요. 예를 들어, `elice`라는 아이디에 비밀번호 `1234`를 가진 사용자를 만들면서 이 사용자는 내 컴퓨터(`localhost`)에서만 접속할 수 있도록 하려면 `CREATE USER elice@localhost IDENTIFIED BY '1234';`라고 입력합니다. 만약 인터넷에 연결된 다른 컴퓨터에서도 이 계정으로 접속하게 하고 싶다면 `localhost` 대신 `'%'`를 사용하면 돼요.

- **권한 주기**: `GRANT` 명령어로 사용자에게 데이터베이스 사용 권한을 줄 수 있어요. `ALL PRIVILEGES`는 모든 권한을 주겠다는 뜻이고, `ON 데이터베이스명.테이블명`은 어떤 데이터베이스의 어떤 테이블에 대한 권한인지 지정하는 거예요. 예를 들어 `shared_kickboard` 데이터베이스의 모든 테이블에 `elice` 사용자에게 모든 권한을 주려면 `GRANT ALL PRIVILEGES ON shared_kickboard.* TO elice@localhost;`라고 입력합니다. 권한을 부여했으면 `FLUSH PRIVILEGES;`를 꼭 실행해서 변경 사항을 시스템에 적용해야 합니다.

- **권한 확인하기**: `SHOW GRANTS FOR` 명령어를 사용해서 특정 사용자가 어떤 권한을 가지고 있는지 확인할 수 있습니다.

- **권한 뺏기**: `REVOKE` 명령어를 사용해서 부여했던 권한을 다시 뺏을 수 있습니다. `GRANT`와 반대되는 명령이라고 생각하면 됩니다.

## 8. 인덱스 (Index)

**인덱스(Index)** 는 데이터베이스 테이블의 **검색 속도를 향상**시키기 위한 자료구조입니다. 마치 책의 색인이나 목차처럼, 인덱스가 있으면 원하는 데이터를 빠르게 찾아갈 수 있습니다. 인덱스가 없다면 데이터 검색 시 테이블의 모든 데이터를 하나씩 확인해야 하므로 검색 시간이 오래 걸릴 수 있습니다.

### 🔍쉬운설명

인덱스는 책의 '찾아보기'나 '목차'와 같은 역할을 해요. 책에서 특정 단어나 내용을 찾을 때, 목차나 찾아보기가 없으면 처음부터 끝까지 모든 페이지를 읽어야 하겠죠? 하지만 목차나 찾아보기가 있으면 원하는 내용을 담고 있는 페이지를 바로 찾아갈 수 있어서 시간을 절약할 수 있습니다. 데이터베이스도 마찬가지예요. 인덱스는 데이터베이스 테이블 안에서 특정 데이터를 찾을 때, 모든 데이터를 일일이 뒤져보지 않고 빠르게 원하는 데이터를 찾아낼 수 있도록 도와주는 특별한 구조입니다. 그래서 인덱스를 사용하면 데이터 검색 속도가 훨씬 빨라져요.

---

## 9. 인덱스 사용의 장단점

모든 데이터를 조회하는 경우에는 인덱스가 불필요하며, 오히려 성능 저하를 일으킬 수 있습니다. 예를 들어 `SELECT * FROM shared_kickboard;`와 같이 테이블의 모든 데이터를 조회할 때는 인덱스의 이점이 없습니다. 따라서 **테이블 쿼리의 사용 계획에 맞게 인덱스를 사용해야 합니다.**

인덱스를 사용하면 일반적으로 테이블 조회 속도와 성능이 향상되지만, 다음과 같은 **단점**도 존재합니다.

- 인덱스를 관리하기 위한 **추가 작업**이 필요합니다. (데이터 삽입, 수정, 삭제 시 인덱스도 함께 업데이트되어야 합니다.)
- 인덱스를 저장할 **추가 저장 공간**이 필요합니다.
- 경우에 따라 검색 **성능이 저하**될 수 있습니다. (잦은 데이터 변경이 있는 테이블이나, 모든 데이터를 조회하는 쿼리에서는 비효율적일 수 있습니다.)

### 🔍쉬운설명

인덱스가 좋다고 해서 무조건 인덱스를 만들면 좋을까요? 그렇지는 않습니다. 마치 모든 책에 두꺼운 찾아보기 목록을 다 넣는 것이 비효율적인 것처럼요.

**인덱스가 불필요한 경우**: 만약 데이터베이스에서 모든 데이터를 통째로 다 가져오는 `SELECT *` 같은 명령을 자주 사용한다면, 굳이 인덱스가 필요 없어요. 어차피 모든 데이터를 다 봐야 하니까요. 이런 경우에는 인덱스를 만드는 것이 오히려 컴퓨터 자원만 낭비하고 속도를 느리게 할 수 있습니다.

인덱스의 단점은 다음과 같습니다.

- **추가 작업 필요**: 데이터베이스에 새로운 데이터가 추가되거나, 기존 데이터가 수정되거나 삭제될 때, 인덱스도 함께 업데이트되어야 해요. 이 과정에서 추가적인 작업이 발생하여 성능이 느려질 수 있습니다.
- **저장 공간 필요**: 인덱스 자체도 데이터이기 때문에 저장 공간을 차지해요. 인덱스가 많아질수록 데이터베이스의 크기도 커지게 됩니다.
- **성능 저하 가능성**: 데이터가 자주 바뀌는 테이블에 인덱스를 많이 만들면, 인덱스를 업데이트하는 작업 때문에 오히려 전체적인 성능이 떨어질 수 있어요.

그래서 인덱스는 언제 어디에 만들지 신중하게 결정해야 합니다.

---

## 10. 인덱스 사용 전략

인덱스를 사용하면 좋은 경우는 다음과 같습니다.

- **규모가 큰 테이블**: 데이터가 매우 많은 테이블에서 특정 데이터를 찾을 때 효율적입니다.
- **업데이트 비용이 적은 컬럼**: 데이터의 삽입, 수정, 삭제 작업이 많지 않아 인덱스 변경이 잦지 않은 경우에 유리합니다.
- **`WHERE` 조건절이나 `ORDER BY`(정렬), `JOIN`을 자주 하는 컬럼**: 검색, 정렬, 조인 작업의 기준이 되는 컬럼에 인덱스를 생성하면 성능이 크게 향상됩니다.
- **데이터의 중복도가 낮은 컬럼**: 고유하거나 거의 고유한 값들이 많은 컬럼에 인덱스를 만드는 것이 효과적입니다. (예: 주민등록번호, 회원 ID 등)

### 🔍쉬운설명

언제 인덱스를 만들면 가장 효과적일까요? 다음과 같은 상황에서 인덱스가 빛을 발합니다.

- **데이터가 아주 많은 테이블**: 방대한 양의 데이터가 있는 큰 도서관에서 특정 책을 찾을 때, 도서관 전체를 다 뒤지는 것보다 색인표를 보는 것이 훨씬 빠르겠죠? 데이터가 많은 테이블일수록 인덱스의 효과가 커집니다.

- **데이터가 잘 변하지 않는 컬럼**: 인덱스는 데이터가 바뀔 때마다 업데이트해야 하므로, 데이터가 자주 바뀌는 곳에 만들면 오히려 인덱스를 업데이트하는 데 시간이 오래 걸릴 수 있어요. 따라서 자주 변경되지 않는 이름, 아이디 같은 컬럼에 만드는 것이 좋습니다.

- **`WHERE` 조건이나 `ORDER BY`, `JOIN`에 자주 쓰이는 컬럼**: '이름이 김철수인 사람을 찾아라'(`WHERE`), '성적 순으로 정렬해라'(`ORDER BY`), '회원 정보와 주문 정보를 합쳐라'(`JOIN`)와 같이 특정 조건으로 데이터를 찾거나, 정렬하거나, 다른 테이블과 연결할 때 자주 사용되는 컬럼에 인덱스를 만들면 작업 속도가 매우 빨라집니다.

- **중복되는 값이 적은 컬럼**: '학년'처럼 1학년, 2학년, 3학년 몇 가지 값만 있는 컬럼보다는 '학번'처럼 사람마다 고유한 값을 가지는 컬럼에 인덱스를 만들 때 더 효율적입니다. 중복되는 값이 많으면 인덱스를 사용해도 결국 여러 데이터를 찾아봐야 할 수 있기 때문입니다.

## 11. 인덱스 추가 및 확인/삭제

```sql
-- 인덱스 추가
CREATE INDEX 인덱스명 ON 테이블명 (컬럼1, 컬럼2, ...);

-- 예시: customer 테이블의 id 컬럼에 customer_id 인덱스 생성
CREATE INDEX customer_id ON customer (id);

-- 인덱스 확인
SHOW INDEX FROM 테이블명;

-- 인덱스 삭제
ALTER TABLE 테이블명 DROP INDEX 인덱스명;

-- 예시: customer 테이블에서 customer_index 인덱스 삭제
ALTER TABLE customer DROP INDEX customer_index;
```

### 🔍쉬운설명

인덱스를 만들고, 확인하고, 지우는 방법입니다.

- **인덱스 추가**: `CREATE INDEX` 명령어를 사용해서 인덱스를 만듭니다. 인덱스명은 이 인덱스의 이름이고, `ON 테이블명`은 어떤 테이블에 만들 것인지, 괄호 안의 `(컬럼1, 컬럼2, ...)`는 어떤 컬럼(들)을 기준으로 인덱스를 만들 것인지 지정하는 거예요. 예를 들어, `customer` 테이블의 `id` 컬럼에 `customer_id`라는 이름으로 인덱스를 만들고 싶으면 `CREATE INDEX customer_id ON customer (id);`라고 입력합니다.

- **인덱스 확인**: `SHOW INDEX FROM 테이블명;` 명령어를 사용하면 해당 테이블에 어떤 인덱스들이 만들어져 있는지 목록을 볼 수 있습니다. 인덱스의 이름, 적용된 컬럼, 타입 등의 정보를 확인할 수 있어요.

- **인덱스 삭제**: `ALTER TABLE 테이블명 DROP INDEX 인덱스명;` 명령어를 사용해서 더 이상 필요 없는 인덱스를 삭제할 수 있습니다. 예를 들어, `customer` 테이블에서 `customer_index`라는 인덱스를 지우고 싶으면 `ALTER TABLE customer DROP INDEX customer_index;`라고 입력하면 됩니다.
