# 데이터베이스 개요

이 강의 자료는 데이터베이스의 기본 개념을 소개하고, 데이터와 정보의 차이, 데이터베이스의 정의와 필요성, 그리고 주요 특징을 설명합니다. 또한, **관계형 데이터베이스(RDB)** 와 **NoSQL 데이터베이스**의 종류와 특징을 비교하고, 관계형 데이터베이스를 생성, 수정, 삭제하는 SQL 명령어를 구체적인 예시와 함께 다룹니다. 마지막으로 SQL의 **데이터 정의어(DDL)** 에 대해 자세히 알아봅니다.

---

## 데이터와 정보

- **데이터**: 현실 세계에서 수집된 단순한 사실이나 값들의 모음입니다. (예: "김민준", "서울시 관악구 신림동", "4832-4921-7561")
- **정보**: 특정 목적에 따라 데이터를 해석하거나 가공하여 얻은 **의미 있는 형태**입니다. (예: 김민준이라는 고객의 주소와 주문 번호를 파악하여 특정 고객의 구매 패턴을 분석하는 데 사용될 수 있는 가공된 지식)

### 🔍쉬운설명

우리가 일상에서 접하는 모든 날것의 사실들이 **데이터**라고 생각할 수 있습니다. 예를 들어, 식당에서 손님이 주문한 메뉴("김치찌개", "된장찌개")나 특정 학생의 시험 점수("90점", "85점") 등이 데이터입니다.

반면에 **정보**는 이런 날것의 데이터를 어떤 목적에 맞게 정리하고 분석해서 의미를 부여한 것입니다. 예를 들어, 식당의 메뉴 데이터를 분석해서 "김치찌개가 된장찌개보다 2배 더 많이 팔린다"는 사실을 알게 되면 이것은 정보가 됩니다. 학생들의 시험 점수를 평균 내어 "이번 학기 평균 점수는 88점이다"라고 한다면 이것 또한 정보가 됩니다.

즉, **데이터는 재료**이고 **정보는 그 재료를 요리해서 만든 결과물**이라고 비유할 수 있습니다.

## 데이터베이스 정의

데이터베이스는 한 조직 안에서 **여러 사용자와 응용 프로그램이 데이터들을 통합하여 저장하고 공동으로 사용하는** 운영하는 데이터들의 집합입니다.

### 🔍쉬운설명

데이터베이스는 그냥 데이터를 모아놓은 창고가 아니라, **여러 사람이 함께 사용할 수 있도록 잘 정리하고 관리하는 데이터 창고**라고 생각할 수 있습니다. 예를 들어, 도서관에서 책을 그냥 쌓아두는 것이 아니라, 누가 어떤 책을 빌려갔는지, 어떤 책이 어디에 있는지 등을 모든 사서와 이용자가 함께 확인할 수 있도록 체계적으로 관리하는 것과 같습니다. 이렇게 데이터를 한곳에 모아두고 규칙적으로 관리함으로써 필요한 데이터를 쉽게 찾고, 여러 사람이 동시에 안전하게 사용할 수 있게 됩니다.

## 데이터베이스의 필요성 (파일처리 시스템의 한계)

파일처리 시스템은 다음과 같은 한계를 가지므로 데이터베이스가 필요합니다.

- **데이터 종속의 문제**: 데이터의 구조가 변경되면 해당 데이터를 사용하는 응용 프로그램의 구조도 함께 변경해야 합니다.
- **데이터 중복의 문제**: 응용 프로그램마다 데이터를 별도로 생성하여 관리하기 때문에 같은 데이터가 여러 곳에 중복 저장될 수 있습니다.
- **데이터 무결성 문제**: 데이터가 정확하고 일관된 형태로 유지되기 어렵습니다.
  - **무결성**: 데이터가 정확하고 일관된 형태로 유지되는 것을 의미하며, 데이터의 무결성을 보장한다는 것은 데이터가 안정적으로 보관된다는 뜻입니다.

### 🔍쉬운설명

옛날에는 데이터를 엑셀 파일이나 일반 텍스트 파일처럼 각각의 파일로 관리했습니다. 이걸 **'파일처리 시스템'** 이라고 부릅니다. 이 방식은 간단한 데이터를 다룰 때는 괜찮지만, 데이터가 많아지고 복잡해지면 여러 문제가 발생합니다.

**데이터 종속의 문제 (프로그램과 데이터가 묶여있음)**: 만약 어떤 데이터 파일의 형식이 바뀌면, 그 파일을 사용하는 모든 프로그램도 그 바뀐 형식에 맞춰 고쳐야 합니다. 예를 들어, 학생의 학번을 5자리에서 10자리로 바꾸면, 성적관리 프로그램, 출결 관리 프로그램 등 학번을 사용하는 모든 프로그램을 다 수정해야 합니다. 마치 특정 제품의 포장 방식이 바뀌면 그 제품을 다루는 모든 기계를 다 바꿔야 하는 것과 같습니다.

**데이터 중복의 문제 (같은 데이터가 여러 곳에 존재)**: 각 프로그램이 자기만의 데이터 파일을 가지면, 같은 정보(예: 학생 이름, 주소)가 여러 파일에 중복해서 저장될 수 있습니다. 예를 들어, 학교에서 학생의 전화번호를 성적부 파일에도 저장하고, 동아리 활동 파일에도 저장했다고 가정해봅시다. 학생이 전화번호를 바꾸면 두 파일 모두 업데이트해야 합니다. 만약 한 파일만 업데이트하고 다른 파일은 잊어버린다면, 어떤 것이 진짜 최신 정보인지 알 수 없게 됩니다.

**데이터 무결성 문제 (데이터가 정확하지 않을 수 있음)**: 중복된 데이터가 생기면, 어떤 데이터가 정확한지 보장하기 어렵습니다. 예를 들어, 위에 전화번호 예시처럼 한 파일에는 이전 전화번호가, 다른 파일에는 새 전화번호가 저장되어 있다면 데이터의 **"무결성"** 이 깨진 것입니다. 무결성은 데이터가 항상 정확하고 믿을 수 있는 상태를 유지하는 것을 의미합니다. 데이터베이스는 이런 문제들을 해결하기 위해 등장했습니다.

## 데이터베이스의 특징

데이터베이스는 다음과 같은 주요 특징을 가집니다.

- **실시간 접근성**: 사용자가 원할 때 언제든지 데이터에 접근할 수 있어야 합니다.
- **지속적인 변화**: 데이터의 삽입, 삭제, 갱신을 통해 최신 데이터를 유지해야 합니다.
- **동시 공유**: 여러 사용자가 동시에 데이터베이스를 이용할 수 있어야 합니다.
- **내용에 대한 참조**: 데이터가 저장된 물리적 위치가 아닌, 값을 가지고 데이터를 검색할 수 있어야 합니다.

### 🔍쉬운설명

데이터베이스는 단순한 저장 공간이 아니라, **살아있는 정보 저장소**입니다.

**실시간 접근성**: 필요한 데이터가 있다면 언제든지 바로 꺼내 볼 수 있어야 합니다. 예를 들어, 은행 시스템에서 고객이 계좌 잔액을 조회하면 실시간으로 정확한 잔액을 보여줘야 하는 것과 같습니다. 오늘 입금된 돈이 내일이나 모레가 되어야 잔액에 반영된다면 불편하겠죠?

**지속적인 변화**: 데이터는 고정되어 있지 않고 계속 바뀝니다. 새로운 정보가 들어오면 추가하고(삽입), 필요 없는 정보는 지우고(삭제), 기존 정보가 변경되면 업데이트(갱신)해서 항상 최신 상태를 유지해야 합니다. 마치 온라인 쇼핑몰에서 상품 재고가 계속 변하는 것처럼요.

**동시 공유**: 여러 사람이 동시에 같은 데이터를 보고 수정할 수 있어야 합니다. 예를 들어, 비행기 티켓 예매 시스템에서 여러 사람이 동시에 좌석을 예매하려고 할 때, 한 사람이 예약하는 동안 다른 사람은 그 좌석에 접근할 수 없거나, 혹은 동시에 예약되어 문제가 생기지 않도록 잘 관리되어야 합니다.

**내용에 대한 참조**: 데이터를 찾을 때, "몇 번째 서랍의 몇 번째 칸에 있는 파일"처럼 물리적인 위치를 아는 것이 아니라, "김민준 고객의 주소"처럼 **데이터의 내용을 기반으로** 찾아야 합니다. 즉, 물리적으로 어디에 저장되어 있는지 몰라도, 원하는 데이터의 내용만 알면 찾아낼 수 있어야 합니다. 예를 들어, 도서관에서 책을 찾을 때 "저기 세 번째 책장 아래에서 두 번째 칸에 있는 책"이라고 찾는 것이 아니라, "데이터베이스 개론 책"이라고 검색해서 찾는 것과 같습니다.

## 데이터베이스 구분: RDB와 NoSQL

데이터베이스는 크게 두 가지 유형으로 나눌 수 있습니다.

**RDB (Relational Database)**
- 관계형 모델을 기반으로 하며, `SQL(Structured Query Language)`을 사용하여 데이터를 관리합니다.
- 테이블 간의 관계를 정의하여 데이터를 효율적으로 관리합니다.

**NoSQL (Not only SQL)**
- 데이터 간의 관계를 정의하지 않는 유연한 모델을 이용합니다.
- RDB보다 유연한 데이터 모델을 사용합니다.

### 🔍쉬운설명

데이터베이스는 데이터를 저장하고 관리하는 방법에 따라 크게 **RDB(관계형 데이터베이스)** 와 **NoSQL** 두 종류로 나눌 수 있습니다.

**RDB**는 데이터를 마치 엑셀 표처럼 테이블 형태로 저장하고, 이 테이블들 간에 정해진 '관계'를 맺어 데이터를 관리하는 방식입니다. 예를 들어, '고객 정보' 테이블과 '주문 정보' 테이블이 있고, 이 두 테이블이 '고객 ID'라는 공통된 정보를 통해 서로 연결되어 있는 것이죠. 이렇게 정형화된 데이터를 다룰 때 매우 강력하며, `SQL`이라는 언어를 통해 데이터를 조작합니다. 마치 잘 정리된 도서관 서가처럼 규칙이 명확합니다.

**NoSQL**은 "Not only SQL"의 줄임말로, RDB처럼 엄격한 관계나 테이블 구조에 얽매이지 않는 데이터베이스입니다. 데이터를 저장하는 방식이 훨씬 자유롭고 유연해서, 형태가 자주 바뀌거나 정해지지 않은 데이터를 다룰 때 좋습니다. 마치 자유롭게 물건을 쌓아두는 창고와 비슷해서, 규칙이 덜하지만 빠르게 물건을 넣고 뺄 수 있습니다. **빅데이터**나 **실시간 웹 서비스**처럼 데이터의 양이 많고 변화가 잦은 곳에서 주로 사용됩니다.

## 관계형 데이터베이스 (RDB)

- 데이터를 **행(row)** 과 **열(column)** 을 가지는 테이블로 표현합니다.
- 테이블 간의 관계를 이용하여 데이터를 효과적으로 관리하고 **데이터의 무결성**을 보장합니다.
- 정의된 테이블 스키마에 맞게 데이터가 삽입되므로 **데이터의 안정성**을 보장합니다.
- 데이터의 구조가 일관적인 경우에 주로 사용됩니다.

### 🔍쉬운설명

관계형 데이터베이스(RDB)는 데이터를 스프레드시트(엑셀) 같은 **표 형태**로 정리해서 저장하는 방식입니다.

**행과 열을 가지는 테이블**: 마치 엑셀 시트처럼, 데이터는 여러 개의 칸으로 이루어진 표(테이블) 안에 저장됩니다. 가로줄은 '행(row)'이라고 부르고, 세로줄은 '열(column)'이라고 부릅니다. 예를 들어, '학생'이라는 테이블에는 '학번', '이름', '학과' 등의 열이 있고, 각 학생의 정보가 한 줄씩 행으로 들어갑니다.

**스키마와 테이블 간의 관계**: RDB는 단순히 표 여러 개를 모아놓은 것이 아닙니다. 각 테이블은 서로 연결될 수 있습니다. 예를 들어, '학생' 테이블과 '수강 과목' 테이블이 있다면, '학번'이라는 공통된 정보를 통해 두 테이블이 연결되어 "어떤 학생이 어떤 과목을 듣는지"를 쉽게 알 수 있습니다. 이렇게 관계를 맺어 데이터를 효율적으로 관리하고, 데이터가 중복되거나 잘못되는 것을 막아(무결성 보장) 데이터의 신뢰성을 높입니다.

**안정성**: RDB를 만들 때는 테이블이 어떤 열을 가질지, 각 열에는 어떤 종류의 데이터(숫자, 글자 등)가 들어갈지 미리 정해둡니다. 이것을 **'스키마'** 라고 합니다. 스키마에 맞춰서만 데이터가 들어갈 수 있기 때문에, 엉뚱한 데이터가 들어가는 것을 막아 데이터의 안정성을 보장합니다.

**일관적인 구조**: 데이터의 형태나 규칙이 명확하게 정해져 있고, 자주 바뀌지 않는 경우에 RDB를 사용하면 가장 효과적입니다. 예를 들어, 고객 정보, 제품 목록, 주문 내역 등 정형화된 데이터를 관리하는 데 적합합니다.

## RDBMS의 종류

대표적인 **RDBMS(관계형 데이터베이스 관리 시스템)** 에는 다음과 같은 것들이 있습니다.

- `MySQL`
- `PostgreSQL`
- `MariaDB`

### 🔍쉬운설명

RDBMS는 관계형 데이터베이스를 만들고 관리해주는 소프트웨어들을 말합니다. 우리가 흔히 사용하는 프로그램처럼, RDB라는 방식을 구현한 여러 종류의 RDBMS가 있습니다.

**`MySQL`**: 가장 널리 사용되는 RDBMS 중 하나입니다. 웹 서비스나 대규모 애플리케이션에서 많이 사용되며, 무료로 사용할 수 있다는 장점이 있습니다.

**`PostgreSQL`**: `MySQL`과 함께 인기 있는 오픈소스 RDBMS입니다. **데이터 무결성**과 **표준 SQL 준수**에 강점을 가지고 있으며, 복잡하고 대용량의 데이터를 다루는 데 적합합니다.

**`MariaDB`**: `MySQL`의 개발자가 `MySQL`의 한계점을 보완하고 오픈소스 정신을 지키기 위해 만든 RDBMS입니다. `MySQL`과 높은 호환성을 가지며, 성능과 보안이 강화된 버전으로 볼 수 있습니다.

이외에도 `Oracle`, `SQL Server` 등 유료 RDBMS도 많이 있습니다. 어떤 RDBMS를 선택할지는 프로젝트의 규모, 요구사항, 예산 등에 따라 달라집니다.

---

## NoSQL

- 데이터를 저장할 수 있는 유형의 제한이 없습니다.
- 새로운 유형의 데이터를 추가하기 용이합니다.
- 데이터의 구조가 **일관적이지 않고 자주 변경되는 경우**에 적합합니다.
- **대용량의 데이터**를 더 빠르게 처리할 수 있습니다.

### 🔍쉬운설명

NoSQL은 RDB와 달리 데이터를 표 형태로 고정해서 저장하지 않습니다. 그래서 RDB가 가진 제약에서 벗어나 더 유연하게 데이터를 다룰 수 있습니다.

**유형 제한 없음**: RDB는 미리 정해진 열(컬럼)에 맞춰서만 데이터를 넣을 수 있지만, NoSQL은 어떤 형태의 데이터든 자유롭게 저장할 수 있습니다. 예를 들어, 어떤 고객의 정보에는 전화번호가 있지만, 다른 고객의 정보에는 이메일만 있을 수도 있습니다.

**새로운 데이터 추가 용이**: 만약 기존 데이터 구조에 새로운 정보를 추가하고 싶을 때, RDB에서는 테이블 구조를 변경해야 하는 복잡한 과정을 거쳐야 합니다. 하지만 NoSQL은 그냥 새로운 정보를 추가하면 되기 때문에 훨씬 쉽습니다.

**유연한 구조에 적합**: 데이터의 형태가 자주 바뀌거나, 애초에 정해진 구조가 없는 경우(예: 소셜 미디어의 게시물, 센서 데이터 등)에 NoSQL이 매우 유리합니다.

**대용량 데이터 처리**: NoSQL은 데이터를 여러 대의 서버에 분산하여 저장하고 처리하기 쉽게 설계되어 있어서, 어마어마하게 많은 양의 데이터를 RDB보다 훨씬 빠르게 처리할 수 있습니다. 그래서 빅데이터나 실시간 데이터를 다루는 서비스에서 많이 활용됩니다.

---

## NoSQL의 종류

대표적인 NoSQL 데이터베이스에는 다음과 같은 것들이 있습니다.

- `MongoDB`
- `Redis`
- `Apache Cassandra`

### 🔍쉬운설명

NoSQL도 RDB처럼 여러 종류가 있으며, 각각 데이터를 저장하는 방식과 특징이 조금씩 다릅니다.

**`MongoDB`**: 가장 유명한 문서(Document) 기반 NoSQL 데이터베이스입니다. 데이터를 `JSON`과 유사한 형태의 문서로 저장하며, 유연한 스키마 덕분에 개발이 빠르고 쉽습니다.

**`Redis`**: In-memory 데이터 구조 저장소입니다. 데이터를 메모리에 저장하여 매우 빠른 읽기/쓰기 성능을 제공하며, **캐싱**(데이터를 임시로 저장하여 빠르게 접근), 세션 관리, 실시간 순위표 등 다양한 용도로 사용됩니다.

**`Apache Cassandra`**: 분산형 데이터베이스로, 대용량 데이터를 여러 서버에 걸쳐 저장하며 **높은 가용성과 확장성**을 제공합니다. 페이스북에서 개발했으며, 엄청난 양의 데이터를 안정적으로 처리해야 하는 경우에 적합합니다.

이외에도 `Couchbase`, `DynamoDB`, `Neo4j` 등 다양한 NoSQL 데이터베이스가 있습니다.

---

## RDB vs NoSQL

| 특징 | RDB (관계형 데이터베이스) | NoSQL (Not only SQL) |
|------|--------------------------|----------------------|
| 데이터 표현 | 행과 열로 구성된 테이블 | 고정적이지 않음 (문서, 키-값, 그래프 등) |
| 데이터 관리 | 관계 모델 기반, 테이블 간의 관계 정의 | 관계 정의 없음, 유연한 모델 |
| 주요 특징 | 데이터의 무결성과 안정성 중요, 정형화된 데이터에 적합 | 데이터 구조 유연, 대용량 데이터 처리, 비정형 데이터에 적합 |
| 대표 예시 | `MySQL`, `PostgreSQL`, `MariaDB` | `MongoDB`, `Redis`, `Apache Cassandra` |

**언제 어떤 DB를 사용할 것인가?**

- **RDB 선택**: 데이터의 구조가 명확하고, 데이터의 무결성과 안정성이 매우 중요하며, 데이터 간의 복잡한 관계를 관리해야 할 때. (예: 은행 시스템, 쇼핑몰 주문 시스템)
- **NoSQL 선택**: 데이터의 구조가 유연하고 자주 변경되거나, 대용량의 비정형/반정형 데이터를 빠르게 처리해야 하며, 높은 확장성이 요구될 때. (예: 소셜 미디어 피드, 실시간 센서 데이터, 로그 데이터)

### 🔍쉬운설명

RDB와 NoSQL은 각각 장단점이 있어서, 어떤 상황에 어떤 데이터베이스를 써야 할지 아는 것이 중요합니다. 마치 **망치와 드라이버가 서로 다른 용도**에 쓰이는 것처럼요.

**RDB**: 엄격하고 규칙적인 방식입니다. 데이터를 표(테이블)로 깔끔하게 정리하고, 이 표들 사이의 관계를 명확히 정의합니다. 그래서 데이터가 정확하고 일관성 있게 유지되는 것이 아주 중요할 때 (예: 은행 거래 내역, 쇼핑몰 주문 정보) 사용합니다. 모든 정보가 완벽하게 맞아떨어져야 하는 경우에 딱 맞습니다.

**NoSQL**: 자유롭고 유연한 방식입니다. 데이터의 형태가 정해져 있지 않거나 자주 바뀌어도 쉽게 저장할 수 있습니다. 데이터 양이 엄청나게 많고, 빠르게 처리해야 할 때 (예: 페이스북 게시물, 실시간 채팅 메시지) 유용합니다. 모든 정보가 완벽하게 일관적일 필요는 없고, 대신 속도와 유연성이 중요할 때 사용합니다.

**언제 무엇을 쓸까?** 만약 "은행 계좌 잔액"처럼 돈이 1원도 틀리면 안 되는 아주 중요한 데이터이고, 데이터의 구조도 미리 명확하게 정의할 수 있다면 **RDB**를 사용하는 것이 좋습니다. 하지만 "사용자들의 쇼핑몰 검색 기록"처럼 데이터의 형태가 다양하고, 계속 새로운 정보가 추가되며, 엄청난 양을 빠르게 처리해야 한다면 **NoSQL**이 더 적합할 수 있습니다. 즉, 프로젝트의 성격과 데이터의 종류, 중요도에 따라 적절한 데이터베이스를 선택해야 합니다.

## 관계형 데이터베이스의 구성 요소

관계형 데이터베이스는 **테이블**이라는 기본 단위로 데이터를 저장하며, 테이블은 다음과 같은 요소들로 구성됩니다.

- **테이블 (table)**: 행과 열로 구성된 데이터 저장의 기본 단위입니다.
- **속성 (attribute)**: 데이터의 특성을 나타내는 가장 작은 논리적 단위로, 테이블의 열(column)을 의미합니다.
- **튜플 (tuple)**: 속성들이 모여 구성된 각각의 행(row)을 의미하며, 하나의 레코드(record)에 해당합니다.
- **도메인 (domain)**: 속성이 가질 수 있는 값의 집합을 의미합니다. (예: '이름' 속성의 도메인은 모든 한글 이름이 될 수 있고, '성별' 속성의 도메인은 '남' 또는 '여'로 제한될 수 있습니다.)

**고객 테이블 (table)**

| ID | 이름 | 주소 |
|:---|:-----|:-----|
| kmax6 | 김민준 | 서울시 관악구 신림동 | ← 튜플 (tuple)
| flykite | 이서연 | 서울시 동작구 대방동 |
| freeman123 | 박서준 | 서울시 관악구 신림동 |

↑ 속성 (attribute) 또는 열 (column)

**도메인 (domain)**: `ID`는 문자열, `이름`은 문자열, `주소`는 문자열 값을 가질 수 있는 집합

### 🔍쉬운설명

관계형 데이터베이스는 데이터를 표(테이블) 형태로 저장한다고 했죠? 이 표를 구성하는 각 부분이 어떤 이름으로 불리는지 알아보겠습니다.

**테이블 (table)**: 가장 큰 단위로, 엑셀 시트 전체라고 생각하면 됩니다. 예를 들어 '고객 정보'를 담는 하나의 표가 바로 테이블입니다.

**속성 (attribute) 또는 열 (column)**: 테이블의 세로줄입니다. 예를 들어, '고객 정보' 테이블에 '이름', '주소', '전화번호' 같은 항목들이 있다면, 이 각각이 속성 또는 열이 됩니다. 각 속성은 어떤 종류의 데이터(예: 문자, 숫자)를 담을지 결정합니다.

**튜플 (tuple) 또는 행 (row)**: 테이블의 가로줄입니다. 각 튜플은 한 사람이나 하나의 대상에 대한 완전한 정보를 담고 있습니다. 예를 들어, '고객 정보' 테이블에서 "김민준, 서울시 관악구 신림동, 010-1234-5678"이라는 한 줄의 정보가 바로 하나의 튜플이 됩니다.

**도메인 (domain)**: 특정 속성이 가질 수 있는 값들의 범위를 말합니다. 예를 들어, '성별' 속성의 도메인은 '남자' 또는 '여자'만 될 수 있습니다. '나이' 속성의 도메인은 0 이상의 정수만 될 수 있습니다. 이는 **데이터가 잘못 입력되는 것을 막아주는 역할**을 합니다.

이 네 가지 요소들이 유기적으로 결합하여 관계형 데이터베이스의 데이터를 구성하고 관리합니다.

## 관계를 통한 데이터 관리의 이점

테이블 간의 관계를 정의하면 **데이터 중복을 줄이고 효율적으로 관리**할 수 있습니다.

**관계가 없을 때 (데이터 중복 발생)**: 주문번호를 고객 ID, 이름, 주소와 함께 관리해야 합니다. 고객별로 여러 번의 주문이 있을 경우, 이름과 주소 데이터가 각 주문마다 중복 저장되어야 합니다.

| ID | 이름 | 주소 | 주문번호 |
|:---|:-----|:-----|:---------|
| kmax6 | 김민준 | 서울시 관악구 신림동 | 4832-4921-7561 |
| flykite | 이서연 | 서울시 동작구 대방동 | 1987-9635-9985 |
| freeman123 | 박서준 | 서울시 관악구 신림동 | 5874-8782-9652 |
| kmax6 | 김민준 | 서울시 관악구 신림동 | 8226-9997-4123 |

**관계가 있을 때 (데이터 효율적 관리)**: 고객 정보 테이블과 주문 정보 테이블을 분리하고, `ID`라는 공통 속성을 통해 두 테이블을 연결합니다. 이렇게 하면 이름과 주소는 고객 정보 테이블에 한 번만 저장되고, 주문 정보 테이블에는 고객 ID만 저장하여 중복을 피할 수 있습니다.

**고객 테이블**

| ID | 이름 | 주소 |
|:---|:-----|:-----|
| kmax6 | 김민준 | 서울시 관악구 신림동 |
| flykite | 이서연 | 서울시 동작구 대방동 |
| freeman123 | 박서준 | 서울시 관악구 신림동 |

**주문 테이블**

| ID | 주문번호 |
|:---|:---------|
| kmax6 | 4832-4921-7561 |
| flykite | 1987-9635-9985 |
| kmax6 | 5874-8782-9652 |
| freeman123 | 8226-9997-4123 |

### 🔍쉬운설명

데이터베이스에서 **'관계'** 는 여러 개의 테이블을 서로 연결하여 데이터를 효율적으로 관리하는 중요한 개념입니다.

예를 들어, 쇼핑몰에 '고객' 정보와 '주문' 정보가 있다고 해봅시다.

**관계가 없을 때**: 만약 모든 정보를 하나의 큰 표에 다 넣는다면 어떻게 될까요? 고객이 물건을 주문할 때마다 고객의 이름, 주소, 전화번호 같은 개인 정보까지 주문 내역에 계속 적어 넣어야 합니다. 김민준 고객이 세 번 주문하면 김민준의 이름과 주소가 세 번 반복해서 저장될 겁니다. 이렇게 되면 데이터가 중복되고, 김민준의 주소가 바뀌면 세 번 다 고쳐야 하는 번거로움과 실수할 가능성이 생깁니다.

**관계가 있을 때**: 데이터베이스는 이런 문제를 해결하기 위해 '고객 정보'는 '고객 테이블'에 따로 저장하고, '주문 정보'는 '주문 테이블'에 따로 저장합니다. 그리고 두 테이블을 연결해주는 공통된 정보(예: 고객 ID)를 통해 서로 관계를 맺습니다.

- **고객 테이블**: 각 고객의 ID, 이름, 주소만 딱 한 번 저장합니다.
- **주문 테이블**: 어떤 고객(ID로 연결)이 어떤 주문번호로 주문했는지 정보만 저장합니다.

이렇게 하면 김민준 고객의 정보는 고객 테이블에 한 번만 저장되고, 주문 테이블에서는 단순히 '김민준 고객의 ID'만 이용해서 주문 내역을 기록할 수 있습니다. 김민준의 주소가 바뀌어도 고객 테이블에서 한 번만 수정하면 되므로 훨씬 효율적이고 정확하게 데이터를 관리할 수 있습니다. 이것이 바로 **관계형 데이터베이스의 핵심 장점**입니다.

## 테이블 정의하기 (`CREATE TABLE`)

테이블을 정의할 때는 `CREATE TABLE` 문을 사용하며, 각 속성(컬럼)의 이름과 데이터 타입, 그리고 제약조건을 명시합니다.

**기본 문법:**

```sql
CREATE TABLE 테이블명(
    속성1 데이터타입1 제약조건1,
    속성2 데이터타입2 제약조건2,
    ...
);
```

**예시: `customer` 테이블 생성**

```sql
CREATE TABLE customer(
    id      VARCHAR(10) NOT NULL,
    name    VARCHAR(10) NOT NULL,
    address VARCHAR(30) NULL
);
```

- `VARCHAR(n)`: n bytes 크기의 **가변 길이 문자열** 데이터를 저장합니다.
- `NOT NULL`: 해당 속성(컬럼)에 `NULL`(비어 있는 값)이 들어갈 수 없도록 합니다.
- `NULL`: 해당 속성(컬럼)에 `NULL` 값이 허용됩니다.

### 🔍쉬운설명

데이터베이스에서 표(테이블)를 만들려면, 어떤 이름의 표를 만들고, 그 표 안에 어떤 종류의 정보(열/속성)를 넣을지 미리 정해줘야 합니다. 이때 사용하는 명령어가 **`CREATE TABLE`** 입니다.

`CREATE TABLE`은 말 그대로 **"테이블을 생성하라"** 는 명령어입니다.

- **테이블명**: 만들고 싶은 표의 이름을 정합니다. 예를 들어 `customer`(고객)처럼요.
- **속성 데이터타입 제약조건**: 이 부분이 중요합니다. 테이블 안에 어떤 열(컬럼)을 만들고, 그 열에 어떤 종류의 데이터(숫자, 문자, 날짜 등)를 저장할지, 그리고 어떤 규칙을 적용할지 정합니다.
  - **속성**: 열의 이름입니다. `id`, `name`, `address`처럼요.
  - **데이터타입**: 그 열에 어떤 종류의 데이터가 들어갈지 지정합니다.
    - `VARCHAR(10)`: '가변 길이 문자열'을 의미하며, 최대 10글자까지 저장할 수 있습니다.
    - `INT`: 정수(예: 1, 2, 3)를 저장합니다.
    - `FLOAT`: 소수점이 있는 숫자(예: 3.14)를 저장합니다.
    - `DATETIME`: 날짜와 시간(예: 2023-10-27 14:30:00)을 저장합니다.
  - **제약조건**: 그 열에 들어갈 데이터에 대한 규칙입니다.
    - `NOT NULL`: 이 열에는 절대로 빈칸(`NULL`)을 넣을 수 없다는 뜻입니다. 예를 들어, 고객 ID나 이름은 반드시 있어야 하므로 `NOT NULL`로 지정할 수 있습니다.
    - `NULL`: 이 열은 빈칸(`NULL`)이 허용된다는 뜻입니다. 주소는 필수가 아닐 수도 있으니 `NULL`로 지정할 수 있습니다.

이렇게 `CREATE TABLE` 명령어를 사용해서 데이터베이스에 새로운 표의 틀을 만드는 것입니다. 일단 표의 틀이 만들어져야 그 안에 데이터를 채워 넣을 수 있겠죠?

## 데이터 타입

데이터 타입은 각 속성이 저장할 수 있는 **값의 종류와 크기**를 정의합니다.

- `VARCHAR(n)`: n Bytes 크기의 가변 길이 문자열 데이터
- `INT`: 정수형 숫자 데이터 (4Bytes)
- `FLOAT`: 부동 소수점 숫자 데이터 (4Bytes)
- `DATETIME`: 날짜와 시간 형태의 기간 데이터 (`YYYY-MM-DD HH:MM:SS`)

제공되는 데이터 타입은 **DBMS(데이터베이스 관리 시스템)** 마다 차이가 있을 수 있습니다.

MySQL 데이터 타입 참고: https://dev.mysql.com/doc/refman/8.0/en/data-types.html

### 🔍쉬운설명

데이터를 저장할 때, 단순히 '숫자'나 '글자'라고만 하면 컴퓨터는 정확히 얼마나 공간을 준비해야 할지, 어떻게 다뤄야 할지 알 수 없습니다. 그래서 각 데이터가 어떤 종류인지 구체적으로 알려주는 것이 **'데이터 타입'** 입니다. 마치 물건을 담을 때 '액체', '고체', '가루'에 따라 다른 용기를 사용하는 것과 같습니다.

**`VARCHAR(n)`**: "Variable Character"의 줄임말로, 길이가 변하는 문자열을 저장할 때 씁니다. `n`은 최대 길이를 의미합니다. 예를 들어 `VARCHAR(10)`이면 최대 10글자까지 저장할 수 있지만, '홍길동'처럼 3글자만 저장하면 3글자만큼의 공간만 사용하고 나머지는 효율적으로 아낍니다. 이름, 주소 등 길이가 가변적인 텍스트에 적합합니다.

**`INT`**: "Integer"의 줄임말로, 소수점이 없는 정수를 저장합니다. 주로 나이, 개수, 코드 번호 등에 사용됩니다. 보통 4바이트 크기로, 대략 -20억부터 20억까지의 숫자를 저장할 수 있습니다.

**`FLOAT`**: 소수점이 있는 실수(부동 소수점)를 저장합니다. 키(175.5cm), 몸무게(70.3kg), 가격(12900.50원) 등에 사용됩니다. 정확도에 따라 `DOUBLE` 같은 더 큰 데이터 타입도 있습니다.

**`DATETIME`**: 날짜와 시간을 함께 저장합니다. `YYYY-MM-DD HH:MM:SS` 형식으로, 예를 들어 '2023-10-27 10:30:00'과 같이 저장됩니다. 글이 작성된 시간, 이벤트 시작 시간 등을 기록할 때 유용합니다.

이외에도 `BOOLEAN`(참/거짓), `DATE`(날짜만), `TIME`(시간만) 등 다양한 데이터 타입이 있으며, 사용하는 데이터베이스 시스템(`MySQL`, `PostgreSQL` 등)에 따라 조금씩 다를 수 있습니다. **데이터 타입을 잘 선택해야 데이터가 정확하게 저장되고, 저장 공간도 효율적으로 사용**할 수 있습니다.

## 정의한 테이블 확인하기 (`SHOW TABLES`, `DESCRIBE` / `DESC`)

생성된 테이블의 목록이나 구조를 확인하는 명령입니다.

**데이터베이스의 테이블 목록 확인:**

```sql
SHOW TABLES;
```

**테이블의 구조 확인 (스키마 확인):**

```sql
DESCRIBE 테이블명;
-- 또는
DESC 테이블명;
```

**예시:**

```sql
DESC customer;
```

### 🔍쉬운설명

테이블을 만들었다면, 잘 만들어졌는지, 어떤 테이블들이 있는지 확인하고 싶을 때가 있습니다. 이때 사용하는 명령어가 `SHOW TABLES`와 `DESCRIBE`입니다.

**`SHOW TABLES;`**: 이 명령어는 현재 데이터베이스에 어떤 테이블들이 있는지 목록을 보여줍니다. 마치 서재에 어떤 책꽂이들이 있는지 이름을 쭉 보여주는 것과 같습니다. 예를 들어, `customer`라는 테이블과 `product`라는 테이블을 만들었다면, `customer`, `product`라고 출력될 것입니다.

**`DESCRIBE 테이블명;` (또는 `DESC 테이블명;`)**: 이 명령어는 특정 테이블의 자세한 구조(스키마)를 보여줍니다. 즉, 그 테이블이 어떤 열(컬럼)들을 가지고 있는지, 각 열의 데이터 타입은 무엇인지, `NULL`을 허용하는지 등의 정보를 보여줍니다. 마치 특정 책꽂이에 어떤 종류의 칸들이 몇 개나 있는지, 각 칸에는 어떤 종류의 책을 넣을 수 있는지 상세히 알려주는 것과 같습니다. 예를 들어 `DESC customer;`를 실행하면 `customer` 테이블의 `id`, `name`, `address` 열과 각각의 데이터 타입, `NULL` 허용 여부 등을 확인할 수 있습니다.

## SQL 작성 규칙

- **SQL 문법은 대문자**로 작성하는 것을 권장합니다. (가독성 향상)
- **테이블명, 속성명은 소문자**로 작성하는 것을 권장합니다.
- 이름은 항상 **의미가 잘 드러나도록** 작성합니다.
- 이름에 여러 단어를 혼합하는 경우 `_`(언더스코어)를 이용하여 구분합니다. (예: `order_id`)
- `--`을 이용하여 **주석**을 나타낼 수 있습니다.
- **명령어 끝에는 세미콜론(`;`)을 작성**합니다.

### 🔍쉬운설명

SQL은 컴퓨터와 대화하는 언어인데, 이 언어를 쓸 때도 사람들이 알아보기 쉽도록 몇 가지 약속된 규칙이 있습니다.

**명령어는 대문자로, 이름은 소문자로**: `SELECT`, `FROM`, `CREATE` 같은 SQL 명령어는 대문자로 쓰는 것이 좋습니다. 반면 `customer`, `id`, `name` 같은 테이블이나 열의 이름은 소문자로 쓰는 것이 일반적입니다. 이렇게 하면 명령어와 이름을 쉽게 구분할 수 있어서 코드를 읽기 편해집니다.

**의미 있는 이름**: `a`, `b`, `c` 같은 의미 없는 이름 대신 `product_name`처럼 어떤 정보를 담고 있는지 바로 알 수 있는 이름을 사용해야 합니다. 나중에 코드를 볼 때 훨씬 이해하기 쉽겠죠.

**여러 단어는 언더스코어(`_`)로 구분**: `customer_name`, `customer_id` 처럼 단어와 단어 사이에 언더스코어를 넣어 구분하면 가독성이 높아집니다.

**주석 (`--`)**: 코드에 설명을 추가하고 싶을 때 `--` 뒤에 내용을 씁니다. 이 부분은 컴퓨터가 무시하고 실행하지 않습니다. 나중에 내가 쓴 코드를 다시 보거나 다른 사람이 볼 때 이해를 돕기 위함입니다.

**세미콜론 (`;`)**: 하나의 SQL 명령어가 끝났다는 것을 나타냅니다. 문장의 마침표와 같다고 생각하면 됩니다. 여러 명령어를 이어서 실행할 때 중요합니다.

이 규칙들을 지키면 SQL 코드가 깔끔해지고, 다른 사람과 협업할 때도 훨씬 효율적입니다.

## 데이터 삽입하기 (`INSERT INTO`)

테이블에 새로운 데이터를 추가할 때는 `INSERT INTO` 문을 사용합니다.

**기본 문법:**

```sql
INSERT INTO 테이블명(속성1, 속성2, ...) VALUES(속성값1, 속성값2, ...);
```

- 속성값을 넣지 않는 경우 `default` 값 또는 `NULL`이 삽입됩니다.
- `VALUES` 절에 입력하는 값의 순서와 타입은 `INSERT INTO` 절의 속성 목록과 **일치**해야 합니다.
- 모든 속성에 순서대로 값을 입력하는 경우에는 속성 목록을 **생략**할 수 있습니다.

**예시:**

속성 목록을 명시하여 데이터 삽입 (속성 순서가 달라도 됨):

```sql
INSERT INTO customer (id, name, address)
VALUES('kmax6', '김민준', '서울시 관악구 신림동');
```

속성 목록의 순서를 바꾸어 삽입 (속성 순서는 중요하지 않음, 단 값은 맞춰야 함):

```sql
INSERT INTO customer (name, address, id)
VALUES('이서연', '서울시 동작구 대방동', 'flykite');
```

모든 속성에 순서대로 값을 입력하는 경우 (속성 목록 생략 가능):

```sql
INSERT INTO customer
VALUES('freeman123', '박서준', '서울시 관악구 신림동');
```

### 🔍쉬운설명

테이블의 틀을 만들었다면, 이제 그 안에 실제 데이터를 채워 넣어야 합니다. 이때 사용하는 명령어가 **`INSERT INTO`** 입니다. "어떤 테이블의 어떤 열에 어떤 값을 넣어라"는 뜻입니다.

`INSERT INTO customer (id, name, address)`: 이것은 `customer`라는 테이블의 `id`, `name`, `address` 열에 데이터를 넣겠다는 의미입니다. 괄호 안의 열 이름들은 순서를 바꿔도 상관없지만, 뒤에 나올 `VALUES`의 값들도 그 순서에 맞게 적어줘야 합니다.

`VALUES('kmax6', '김민준', '서울시 관악구 신림동')`: `INSERT INTO` 절에 명시된 열(`id`, `name`, `address`) 순서대로 실제 값을 넣어줍니다. **문자열은 작은따옴표(`'`)로 묶어줍니다.**

**중요한 점:**

- **순서 매칭**: 만약 `INSERT INTO customer (id, name, address)`라고 했다면, `VALUES` 뒤에도 `id` 값, `name` 값, `address` 값 순서로 넣어야 합니다.
- **생략 가능**: 만약 테이블의 모든 열에 순서대로 값을 넣는다면, `(id, name, address)`와 같은 열 목록을 생략하고 `INSERT INTO customer VALUES(...)`처럼 쓸 수도 있습니다. 하지만 보통 명시적으로 열 목록을 쓰는 것이 실수를 줄이고 가독성을 높이는 좋은 습관입니다.
- **값 생략 시**: 만약 특정 열의 값을 넣지 않으면, 그 열에 `default` 값이 설정되어 있다면 그 값이 들어가고, `default` 값이 없으면 `NULL`(비어있는 값)이 들어갑니다. 단, `NOT NULL` 제약조건이 있는 열은 값을 반드시 넣어줘야 합니다.

## 데이터 출력하기 (`SELECT`)

테이블에 저장된 데이터를 조회하고 출력할 때는 `SELECT` 문을 사용합니다.

**기본 문법:**

```sql
SELECT 속성1, 속성2, ... FROM 테이블명;
```

- `FROM 테이블명`: 데이터를 가져올 테이블을 지정합니다.

**예시:**

원하는 특정 속성만 출력:

```sql
SELECT id, name, address FROM customer;
```

결과: `id`, `name`, `address` 컬럼의 데이터만 출력됩니다.

| id | name | address |
|:---|:-----|:--------|
| kmax6 | 김민준 | 서울시 관악구 신림동 |
| flykite | 이서연 | 서울시 동작구 대방동 |
| freeman123 | 박서준 | 서울시 관악구 신림동 |

출력하고 싶은 속성 조정 (순서 변경):

```sql
SELECT address, name FROM customer;
```

결과: `address`와 `name` 컬럼의 데이터가 해당 순서로 출력됩니다.

| address | name |
|:--------|:-----|
| 서울시 관악구 신림동 | 김민준 |
| 서울시 동작구 대방동 | 이서연 |
| 서울시 관악구 신림동 | 박서준 |

`*`을 이용하여 모든 속성 출력:

```sql
SELECT * FROM customer;
```

결과: `customer` 테이블의 모든 컬럼(`id`, `name`, `address`)의 데이터가 출력됩니다.

### 🔍쉬운설명

데이터베이스에 데이터를 넣어두었다면, 이제 그 데이터를 다시 보고 싶을 때가 많겠죠? 이때 사용하는 명령어가 **`SELECT`** 입니다. "어떤 테이블에서 어떤 정보를 선택해서 보여줘"라는 뜻입니다.

`SELECT id, name, address`: 이것은 `id`, `name`, `address`라는 열(속성)들의 데이터를 보고 싶다는 의미입니다. 원하는 열의 이름들을 쉼표(`,`)로 구분하여 나열합니다.

`FROM customer`: `customer`라는 테이블에서 이 정보를 가져오겠다는 의미입니다.

**데이터 출력의 다양한 방법:**

- **특정 열만 보기**: 만약 고객의 `id`와 `name`만 보고 싶다면, `SELECT id, name FROM customer;`라고 하면 됩니다. 필요한 정보만 골라서 볼 수 있습니다.
- **열의 순서 바꾸기**: `SELECT address, name FROM customer;`처럼 `SELECT` 뒤에 적는 순서대로 결과가 나옵니다.
- **모든 열 보기 (`*`)**: 테이블에 있는 모든 열의 데이터를 한 번에 보고 싶다면 `SELECT * FROM customer;`라고 하면 됩니다. `*`은 '모든 것'을 의미합니다.

`SELECT` 명령어는 **데이터베이스에서 가장 많이 사용되는 명령어** 중 하나로, 원하는 데이터를 정확하게 찾아내고 분석하는 데 필수적입니다.

## SQL (Structured Query Language)

SQL은 **관계형 데이터베이스를 활용하기 위해 사용하는 표준 언어**입니다. SQL은 기능에 따라 크게 세 가지 유형으로 나뉩니다.

**데이터 정의어 (DDL, Data Definition Language)**
- 테이블과 같은 **데이터 구조를 정의**하는 데 사용됩니다.
- 주요 명령어: `CREATE`(생성), `ALTER`(수정), `DROP`(삭제)

**데이터 조작어 (DML, Data Manipulation Language)**
- 데이터를 **조회, 검색, 삽입, 수정, 삭제**하는 데 사용됩니다.
- 주요 명령어: `SELECT`(조회), `INSERT`(삽입), `UPDATE`(수정), `DELETE`(삭제)

**데이터 제어어 (DCL, Data Control Language)**
- 데이터베이스에 **접근하는 권한을 관리**하는 데 사용됩니다.
- 주요 명령어: `GRANT`(권한 부여), `REVOKE`(권한 취소), `COMMIT`(변경사항 확정), `ROLLBACK`(변경사항 취소)

### 🔍쉬운설명

SQL은 "Structured Query Language"의 줄임말로, 우리가 관계형 데이터베이스와 대화할 때 사용하는 약속된 언어입니다. 마치 컴퓨터에게 "이거 해줘", "저거 보여줘"라고 지시하는 말이라고 생각하면 됩니다. SQL은 하는 역할에 따라 세 가지 종류로 나뉩니다.

**데이터 정의어 (DDL)**: '데이터베이스의 뼈대'를 만드는 언어입니다. 테이블을 만들거나(`CREATE`), 기존 테이블의 구조를 바꾸거나(`ALTER`), 테이블을 완전히 없앨 때(`DROP`) 사용합니다. 건물을 짓기 전에 설계도를 그리고, 벽을 세우고, 필요 없으면 건물을 허무는 작업과 비슷합니다.

**데이터 조작어 (DML)**: '데이터베이스 안의 내용물'을 다루는 언어입니다. 테이블에 데이터를 새로 넣거나(`INSERT`), 이미 있는 데이터를 수정하거나(`UPDATE`), 데이터를 지우거나(`DELETE`), 그리고 가장 많이 쓰는 '데이터를 조회해서 보여줘'(`SELECT`) 같은 작업을 합니다. 건물 안에 가구를 넣고, 가구를 옮기고, 필요 없으면 버리고, 원하는 가구를 찾는 것과 같습니다.

**데이터 제어어 (DCL)**: '데이터베이스 사용 권한'을 관리하는 언어입니다. 누가 데이터베이스에 접근할 수 있는지, 어떤 작업을 할 수 있는지 권한을 주거나(`GRANT`), 빼앗을 때(`REVOKE`) 사용합니다. 또한 작업 내용을 확정하거나(`COMMIT`), 실수했을 때 되돌리는(`ROLLBACK`) 명령어도 여기에 속합니다. 건물에 누가 들어올 수 있고, 어떤 방에 들어갈 수 있는지 허락하거나 금지하는 경비 역할과 비슷합니다.

이렇게 SQL은 세 가지 언어의 집합으로, **데이터베이스를 효율적으로 관리하고 활용하는 데 필요한 모든 기능**을 제공합니다.

## 테이블 수정하기 (`ALTER TABLE`)

`ALTER TABLE` 문은 이미 생성된 테이블의 **구조를 변경**할 때 사용합니다.

**컬럼 추가:**

```sql
ALTER TABLE 테이블명 ADD COLUMN 컬럼명 데이터타입 제약조건;
```

예시: `customer` 테이블에 `birthday` 컬럼(`DATE` 타입, `NULL` 허용) 추가

```sql
ALTER TABLE customer ADD COLUMN birthday DATE NULL;
```

**컬럼 수정 (데이터타입 또는 제약조건 변경):**

```sql
ALTER TABLE 테이블명 MODIFY COLUMN 컬럼명 데이터타입 제약조건;
```

예시: `customer` 테이블의 `id` 컬럼을 `VARCHAR(15)`로 변경하고 `NULL` 허용

```sql
ALTER TABLE customer MODIFY COLUMN id VARCHAR(15) NULL;
```

**컬럼 이름 변경:**

```sql
ALTER TABLE 테이블명 CHANGE COLUMN 기존컬럼명 새로운컬럼명 데이터타입 제약조건;
```

예시: `customer` 테이블의 `name` 컬럼 이름을 `korean_name`으로 변경하고 `VARCHAR(10) NOT NULL`로 변경

```sql
ALTER TABLE customer CHANGE COLUMN name korean_name VARCHAR(10) NOT NULL;
```

**컬럼 삭제:**

```sql
ALTER TABLE 테이블명 DROP COLUMN 컬럼명;
```

예시: `customer` 테이블에서 `address` 컬럼 삭제

```sql
ALTER TABLE customer DROP COLUMN address;
```

**테이블 이름 변경:**

```sql
ALTER TABLE 기존테이블명 RENAME 새로운테이블명;
```

예시: `customer` 테이블 이름을 `member`로 변경

```sql
ALTER TABLE customer RENAME member;
```

### 🔍쉬운설명

데이터베이스에 테이블을 한 번 만들었다고 해서 끝이 아닙니다. 시간이 지나면서 필요한 정보가 추가되거나, 기존 정보의 형식이 바뀌거나, 더 이상 필요 없는 정보가 생길 수 있습니다. 이때 테이블의 구조(뼈대)를 변경하는 명령어가 **`ALTER TABLE`** 입니다. "테이블의 구조를 바꿔라"는 뜻입니다.

**컬럼 추가 (`ADD COLUMN`)**: 새로운 종류의 정보를 테이블에 추가하고 싶을 때 사용합니다. 예를 들어, `customer` 테이블에 `birthday`(생일) 정보를 추가하려면 `ALTER TABLE customer ADD COLUMN birthday DATE NULL;`라고 합니다. 고객들에게 생일을 묻기 시작한 상황이라고 생각하면 됩니다.

**컬럼 수정 (`MODIFY COLUMN`)**: 기존 컬럼의 데이터 타입이나 제약조건을 바꾸고 싶을 때 사용합니다. 예를 들어, `id`의 길이가 10자리에서 15자리로 늘어나야 한다면 `ALTER TABLE customer MODIFY COLUMN id VARCHAR(15) NULL;`라고 수정할 수 있습니다.

**컬럼 이름 변경 (`CHANGE COLUMN`)**: 컬럼의 이름을 바꾸고 싶을 때 사용합니다. 이때 데이터 타입과 제약조건도 함께 명시해야 합니다. `name` 컬럼을 `korean_name`으로 바꾸고 싶다면 `ALTER TABLE customer CHANGE COLUMN name korean_name VARCHAR(10) NOT NULL;`와 같이 사용합니다.

**컬럼 삭제 (`DROP COLUMN`)**: 더 이상 필요 없는 컬럼을 테이블에서 완전히 없애고 싶을 때 사용합니다. `address` 컬럼이 이제 필요 없다면 `ALTER TABLE customer DROP COLUMN address;`라고 합니다. 개인정보 보호 정책상 주소 정보를 더 이상 저장하지 않기로 한 상황 같은 거죠.

**테이블 이름 변경 (`RENAME`)**: 테이블 자체의 이름을 바꾸고 싶을 때 사용합니다. `customer` 테이블 이름을 `member`로 바꾸고 싶다면 `ALTER TABLE customer RENAME member;`라고 합니다.

`ALTER TABLE`은 테이블의 구조를 건드리는 **중요한 명령어**이므로, 신중하게 사용해야 합니다. 기존 데이터에 영향을 줄 수 있기 때문입니다.

---

## 테이블 삭제하기 (`DROP TABLE`)

`DROP TABLE` 문은 데이터베이스에서 테이블을 **완전히 제거**할 때 사용합니다. 테이블뿐만 아니라 해당 테이블에 저장된 **모든 데이터도 함께 삭제**되므로 매우 신중하게 사용해야 합니다.

**기본 문법:**

```sql
DROP TABLE 테이블명;
```

**예시: `member` 테이블을 삭제하는 예시**

```sql
DROP TABLE member;
```

### 🔍쉬운설명

더 이상 필요 없는 테이블은 데이터베이스에서 완전히 지워버릴 수 있습니다. 이때 사용하는 명령어가 **`DROP TABLE`** 입니다. "이 테이블을 삭제해라"는 뜻입니다.

`DROP TABLE member;`: `member`라는 이름의 테이블을 데이터베이스에서 완전히 제거합니다.

**매우 중요!**: `DROP TABLE` 명령어는 테이블의 구조(뼈대)뿐만 아니라, **그 테이블 안에 들어있던 모든 데이터까지 영구적으로 삭제**해버립니다. 삭제된 데이터는 복구하기 매우 어렵거나 불가능할 수 있으므로, 이 명령어를 사용하기 전에는 정말 신중하게 생각하고 필요한 경우 **백업**을 해두어야 합니다. 마치 건물을 허무는 것과 같아서, 한 번 허물면 되돌릴 수 없고 건물 안의 모든 물건들도 함께 사라지는 것과 비슷합니다.

# 데이터베이스 구성하기

본 강의 자료는 데이터베이스를 구성하는 데 필요한 핵심 개념인 **제약 조건**, **키(Key)**, **데이터 모델링**, 그리고 **ER 다이어그램**(Peter Chen 및 IE 표기법)에 대해 다룹니다. 현실 세계의 데이터를 효율적으로 데이터베이스화하고 관리하기 위한 기초 지식을 제공하는 것을 목표로 합니다.

---

## 제약 조건

**제약 조건**은 테이블에 잘못된 데이터가 입력되는 것을 방지하기 위한 규칙으로, **데이터의 무결성을 유지**하는 데 필수적입니다.

**`NOT NULL`**: 특정 속성(열)에 `NULL` 값을 허용하지 않습니다. 데이터를 입력하지 않으면 오류가 발생하며, 아무것도 명시하지 않는 경우 기본적으로 `NULL` 값이 허용됩니다.

```sql
CREATE TABLE customer(
    id   VARCHAR(10),
    name VARCHAR(10) NOT NULL
);

INSERT INTO customer (id, name) VALUES('kmax6', '김민준')  -- 정상 처리
INSERT INTO customer (id)       VALUES('kmax6');           -- 에러 발생
```

**`UNIQUE`**: 특정 속성에 중복되는 값을 허용하지 않습니다. 동일한 값이 이미 존재하면 오류가 발생하지만, `NULL` 값은 비교가 불가능하므로 중복되어도 오류가 발생하지 않습니다.

```sql
CREATE TABLE customer(
    id   VARCHAR(10) UNIQUE,
    name VARCHAR(10) NOT NULL
);

INSERT INTO customer (id, name) VALUES('kmax6', '김민준')  -- 정상 처리
INSERT INTO customer (id, name) VALUES('kmax6', '이서연')  -- 에러 발생 (중복 id)
```

**`DEFAULT`**: 속성에 값을 지정하지 않을 경우 자동으로 설정되는 **기본값**을 정의합니다.

```sql
CREATE TABLE customer(
    id      VARCHAR(10) UNIQUE,
    name    VARCHAR(10) NOT NULL,
    address VARCHAR(30) DEFAULT 'No Address'
);

INSERT INTO customer (id, name)           VALUES('kmax6',   '김민준')                  -- address에 'No Address' 자동 삽입
INSERT INTO customer                      VALUES('flykite',  '이서연', '서울시 동작구 대방동')
```

**`CHECK`**: 속성값의 범위를 제한하여 **특정 조건에 맞는 값만 허용**합니다. 제한된 범위 밖의 값이 입력되면 오류가 발생합니다.

```sql
CREATE TABLE customer(
    id      VARCHAR(10) UNIQUE,
    name    VARCHAR(10) NOT NULL,
    address VARCHAR(30) DEFAULT 'No Address',
    age     INT CHECK (age >= 19)
);

INSERT INTO customer VALUES('kmax6',   '김민준', '서울시 관악구 신림동', 25)  -- 정상 처리
INSERT INTO customer VALUES('flykite', '이서연', '서울시 동작구 대방동', 17)  -- 에러 발생 (age < 19)
```

**`CONSTRAINT`를 이용한 제약 조건 정의**: 제약 조건에 이름을 부여하여 관리할 수 있습니다.

```sql
CREATE TABLE customer(
    id  VARCHAR(10),
    age INT,
    CONSTRAINT id_unique  UNIQUE (id),
    CONSTRAINT age_check  CHECK  (age >= 19)
);
```

생성된 제약 조건은 다음 쿼리를 통해 확인할 수 있습니다.

```sql
SELECT * FROM information_schema.table_constraints;
```

**제약 조건 추가/수정/삭제:**

추가:
```sql
ALTER TABLE 테이블명 ADD CONSTRAINT 제약조건이름 제약조건(속성);

ALTER TABLE customer ADD CONSTRAINT address_unique UNIQUE(address);
ALTER TABLE customer ADD CONSTRAINT customer_chk_2 CHECK(age >= 19);
```

수정 (`DEFAULT` 제약 조건):
```sql
ALTER TABLE 테이블명 ALTER 속성 SET DEFAULT 기본값;

ALTER TABLE customer ALTER address SET DEFAULT '주소 없음';
```

삭제:
```sql
ALTER TABLE 테이블명 DROP CONSTRAINT 제약조건이름;

ALTER TABLE customer DROP CONSTRAINT customer_chk_2;
```

`DEFAULT` 제약 조건 삭제:
```sql
ALTER TABLE 테이블명 ALTER 속성 DROP DEFAULT;

ALTER TABLE customer ALTER address DROP DEFAULT;
```

### 🔍쉬운설명

데이터베이스에서 '제약 조건'은 마치 **건물의 건축 규제**와 같아요. 건물을 지을 때 안전을 위해 높이, 면적, 용도 등을 규제하듯이, 데이터베이스도 데이터의 품질과 일관성을 유지하기 위해 특정 규칙을 적용합니다.

**`NOT NULL`**: "이 칸은 비워둘 수 없습니다!"라는 규칙입니다. 예를 들어, 회원가입 시 '이름'은 절대로 비워둘 수 없게 만드는 것이죠. 만약 이름을 입력하지 않으면 회원가입이 안 됩니다.

**`UNIQUE`**: "이 값은 오직 하나만 존재해야 합니다!"라는 규칙입니다. 예를 들어, 웹사이트에서 아이디는 다른 사람과 중복될 수 없죠? `UNIQUE`가 바로 그런 역할을 합니다. 다만, `NULL`은 '알 수 없음'을 의미해서, 두 개의 '알 수 없음'은 서로 다르다고 보기에 중복 오류가 나지 않습니다.

**`DEFAULT`**: "아무것도 입력하지 않으면 자동으로 이 값으로 채워주세요!"라는 규칙입니다. 예를 들어, 게시판에 글을 쓸 때 작성일을 입력하지 않으면 자동으로 오늘 날짜가 입력되는 것처럼요.

**`CHECK`**: "이 값은 특정 조건을 만족해야 합니다!"라는 규칙입니다. 예를 들어, 특정 서비스는 19세 이상만 가입할 수 있다고 할 때, `CHECK (age >= 19)`와 같은 조건을 걸어 19세 미만은 가입을 막는 것입니다.

**`CONSTRAINT`**: 이런 제약 조건들에 '이름'을 붙여서 관리하는 것입니다. 마치 파일에 이름을 붙여 쉽게 찾고 관리하는 것처럼, 제약 조건에도 이름을 주면 나중에 수정하거나 삭제하기가 훨씬 편해집니다.

이런 제약 조건들을 잘 활용하면 데이터베이스에 엉뚱하거나 잘못된 데이터가 들어가는 것을 막을 수 있고, **항상 깨끗하고 정확한 데이터를 유지**할 수 있습니다.

## 키 (Key)

**키**는 데이터베이스에서 조건에 만족하는 튜플(행)을 찾거나 정렬할 때 **기준이 되는 속성(열)** 입니다.

### 기본키 (Primary Key)

서로 다른 튜플을 **유일하게 식별**할 수 있는 기준이 되는 속성입니다.

- **중복되는 값**을 가질 수 없습니다.
- **`NULL` 값**을 가질 수 없습니다.
- 테이블 당 **1개만** 설정할 수 있습니다.
- 예시: `customer` 테이블의 `id` 속성.
- 설정 방법: `id VARCHAR(10) PRIMARY KEY`

### 외래키 (Foreign Key)

다른 테이블의 기본키를 **참조**하는 속성으로, **테이블 간의 관계를 정의**합니다.

- 참조되는 테이블의 기본키에 없는 값은 지정할 수 없습니다. 즉, **부모 테이블에 없는 자식 테이블의 데이터는 존재할 수 없습니다.**
- 예시: `order_history` 테이블의 `customer_id` 속성은 `customer` 테이블의 `id`를 참조합니다.
- 설정 방법: `FOREIGN KEY (참조할 속성) REFERENCES 참조되는 테이블(참조되는 속성)`

```sql
CREATE TABLE customer(
    id      VARCHAR(10) PRIMARY KEY,
    name    VARCHAR(10),
    address VARCHAR(30)
);

CREATE TABLE order_history(
    customer_id VARCHAR(10),
    order_id    VARCHAR(14),
    FOREIGN KEY (customer_id) REFERENCES customer(id),
    CONSTRAINT order_history_pk PRIMARY KEY (customer_id, order_id)
);
```

### 그 외 키

- **후보키 (Candidate Key)**: 기본키가 될 수 있는 키로, **유일성**(각 튜플을 유일하게 식별)과 **최소성**(속성 하나라도 제거하면 유일성이 깨짐)을 만족합니다. `기본키 ⊆ 후보키`
- **대체키 (Alternate Key)**: 후보키 중에서 기본키로 선택되지 않은 키입니다. `대체키 ⊆ 후보키`
- **슈퍼키 (Super Key)**: 튜플을 유일하게 식별할 수 있는 유일성은 만족하지만, 최소성은 만족하지 않는 키입니다. 즉, **불필요한 속성이 포함**될 수 있습니다.

### 무결성 제약 조건

- **개체 무결성 (Entity Integrity)**: 기본키는 `NULL` 값과 중복된 값을 가질 수 없습니다.
- **참조 무결성 (Referential Integrity)**: 외래키는 `NULL`이거나 참조되는 릴레이션(테이블)의 기본키 값과 동일해야 합니다.
- **도메인 무결성 (Domain Integrity)**: 특정 속성값은 그 속성이 정의된 도메인(데이터 타입 및 제약 조건)에 속한 값이어야 합니다.
- **`NULL` 무결성 (Null Integrity)**: 특정 속성값은 `NULL` 값을 가질 수 없습니다 (`NOT NULL` 제약 조건).
- **고유 무결성 (Unique Integrity)**: 각 튜플이 가지는 속성값들은 서로 달라야 합니다 (`UNIQUE` 제약 조건).
- **키 무결성 (Key Integrity)**: 테이블에 최소 한 개 이상의 키가 존재해야 합니다.

### 🔍쉬운설명

**'키(Key)'** 는 데이터베이스에서 데이터를 찾아내고 분류하는 데 사용하는 **'열쇠'** 같은 역할을 합니다. 각 데이터 덩어리(튜플)를 특정 기준으로 구별하고 연결하는 데 사용되죠.

**기본키 (Primary Key)**: 주민등록번호처럼 어떤 사람을 세상에 하나뿐인 존재로 식별할 수 있게 해주는 **가장 중요한 열쇠**입니다. 이 키는 절대로 중복되어서는 안 되고, 비어있어서도 안 됩니다. 테이블마다 딱 하나만 지정할 수 있어요. 예를 들어, 고객 테이블에서 **고객 ID**가 기본키가 될 수 있습니다.

**외래키 (Foreign Key)**: 다른 테이블의 기본키를 '참조'하는 열쇠입니다. 마치 가족 관계에서 부모님과 자녀가 가족이라는 연결고리를 가지는 것과 같아요. 주문 내역 테이블에 고객 ID가 있다면, 이 고객 ID는 고객 테이블의 고객 ID(기본키)를 참조하는 외래키가 됩니다. 이 외래키 덕분에 어떤 주문이 어떤 고객에게서 왔는지 알 수 있죠. **외래키의 값은 반드시 참조하는 테이블의 기본키에 존재하는 값이어야 합니다.**

**후보키**: 기본키가 될 자격이 있는 여러 열쇠들입니다. 유일하게 식별할 수 있고, 더 이상 줄일 수 없는 최소한의 정보만으로 구성된 키를 말합니다.

**대체키**: 후보키 중에서 기본키로 선택받지 못한 나머지 열쇠들입니다.

**슈퍼키**: 유일하게 식별할 수 있지만, 필요 없는 정보(속성)를 더 많이 가지고 있는 열쇠입니다. 예를 들어, `(고객 ID, 고객 이름)` 이렇게 두 개를 묶어서도 고객을 식별할 수는 있지만, 고객 ID만으로도 충분하므로 `(고객 ID, 고객 이름)`은 슈퍼키가 됩니다.

무결성 제약 조건은 이러한 키들이 지켜야 할 약속들입니다.

- **개체 무결성**: 기본키는 절대 비어있거나 중복되면 안 된다는 약속.
- **참조 무결성**: 외래키는 참조하는 테이블의 값이 실제로 존재하거나, 아니면 아예 없어야(`NULL`) 한다는 약속. 예를 들어, 존재하지 않는 고객의 주문은 등록될 수 없다는 것이죠.
- **도메인 무결성**: 각 데이터가 정해진 형식(예: 나이는 숫자여야 함, 이름은 문자여야 함)과 조건을 지켜야 한다는 약속.
- **`NULL` 무결성**: 특정 칸은 비워둘 수 없다는 약속.
- **고유 무결성**: 특정 칸의 값은 중복될 수 없다는 약속.
- **키 무결성**: 테이블에는 데이터를 식별할 수 있는 키가 최소한 하나는 있어야 한다는 약속.

이러한 약속들을 통해 데이터베이스의 정보가 항상 정확하고 믿을 수 있도록 유지됩니다.

## 데이터 모델링

**데이터 모델링**은 현실 세계에 존재하는 데이터를 데이터베이스화하는 과정입니다.

### 데이터 모델과 구성 요소

- **데이터 모델**: 현실 세계의 데이터를 단순화하고 추상화하여 표현한 모델입니다.
- **개체 (Entity)**: 데이터로 표현하고자 하는 현실 세계의 개념이나 정보의 단위입니다. (예: 킥보드, 회원)
- **속성 (Attribute)**: 개체에 대한 정보입니다. (예: 킥보드의 브랜드/이용 가격, 회원의 아이디/이름)
- **관계 (Relationship)**: 개체 간의 연관성입니다. (예: 고객은 킥보드를 대여한다)

### 데이터 모델링 과정

- **개념적 설계**: 현실 세계를 추상적 개념으로 표현하는 과정입니다. (예: ERD 작성)
- **논리적 설계**: DBMS가 처리할 수 있는 데이터 구조(스키마)를 설계하는 과정입니다.
- **물리적 설계**: DBMS에 테이블을 저장할 구조를 설계하는 과정입니다.

### 🔍쉬운설명

**'데이터 모델링'** 은 마치 **건물을 짓기 전에 설계도를 그리는 것**과 같습니다. 현실 세계에 흩어져 있는 정보들을 어떻게 데이터베이스라는 건물 안에 체계적으로 정리해서 넣을지 계획하는 과정이죠.

**데이터 모델**: 이 설계도 자체를 '데이터 모델'이라고 합니다. 현실을 아주 간결하고 명확하게 보여주는 그림이나 청사진 같은 것이죠.

**개체 (Entity)**: 설계도에서 가장 중요한 '방'이나 '공간' 같은 것입니다. 예를 들어, '고객'이나 '킥보드'처럼 현실 세계에서 독립적으로 존재하는 중요한 정보의 단위를 말해요.

**속성 (Attribute)**: 각 방의 '가구'나 '색깔' 같은 세부 정보입니다. '고객' 개체라면 '이름', '주소', '전화번호' 같은 정보들이 속성이 되겠죠. '킥보드' 개체라면 '브랜드', '연식', '가격' 등이 속성이 됩니다.

**관계 (Relationship)**: 방과 방 사이의 '복도'나 '문'처럼 개체들이 서로 어떻게 연결되어 있는지를 나타냅니다. 예를 들어, '고객'이 '킥보드'를 '대여한다'는 것이 관계가 됩니다.

데이터 모델링 과정은 설계도를 그리는 3단계와 같아요.

**개념적 설계**: 가장 첫 단계로, '집'을 짓는다고 할 때, '어떤 방들이 필요하고, 방들이 대략적으로 어떻게 연결될까?' 하고 큰 그림을 그리는 단계입니다. 아직은 구체적인 재료나 치수를 생각하지 않고, 아이디어를 정리하는 단계죠.

**논리적 설계**: 이제 개념적 설계에서 나온 아이디어를 바탕으로 좀 더 구체적인 설계도를 그리는 단계입니다. '이 방은 거실이니까 소파랑 TV를 놓아야겠네. 저 방은 침실이니까 침대가 필요해.' 이런 식으로 각 개체(방)들이 어떤 속성(가구)을 가질지, 그리고 어떤 관계(연결)를 가질지 DBMS(데이터베이스 관리 시스템)가 이해할 수 있는 형태로 자세히 설계합니다. 어떤 종류의 데이터(숫자, 문자 등)를 쓸지도 여기서 정해요.

**물리적 설계**: 마지막으로, 실제로 건물을 지을 때 필요한 '콘크리트 몇 톤, 창문 크기는 얼마'와 같은 아주 세부적인 사항들을 결정하는 단계입니다. 데이터베이스에서는 데이터를 저장할 때 어떤 파일 시스템을 쓸지, 인덱스는 어떻게 만들지 등 실제 컴퓨터에 데이터를 어떻게 저장할지에 대한 최적화된 설계를 하는 것입니다.

이러한 과정을 통해 현실의 복잡한 정보를 효율적으로 데이터베이스에 저장하고 관리할 수 있게 됩니다.

## ER 다이어그램 (Peter Chen)

**ERD (Entity-Relationship Diagram)**, 즉 개체-관계 다이어그램은 현실 세계의 데이터를 개체와 관계 형태로 다이어그램으로 나타내는 방법입니다. 표기법에는 **Peter Chen 방식**과 **IE(Information Engineering) 방식**이 있습니다.

ERD 그리기 도구: `app.diagrams.net` (구 draw.io) 같은 온라인 도구를 활용할 수 있습니다.

### Peter Chen 표기법 기호와 의미

| 기호 | 의미 |
|:----:|:-----|
| □ | 개체 (Entity) |
| ◯ | 속성 (Attribute) |
| ◊ | 관계 (Relationship) |
| − | 개체와 속성의 연결 |
| <u>◯</u> | 기본키 (Primary Key) |

### 공유 킥보드 서비스 요구사항 예시

- **고객**: 이름, ID, PW, 전화번호, 생년월일 입력.
- **킥보드**: 고유 ID, 브랜드와 연식에 따른 기본료, 이용 1분당 가격 정보.
- **대여**: 대여 상태, 대여 시간, 대여 위치 기록.
- **제약**: 한 명의 고객은 한 번에 하나의 킥보드만 대여.

### 공유 킥보드 ERD (Peter Chen 방식)

**개체**: 고객, 킥보드, 대여하다 (N:M 관계를 나타내는 개체)

**속성:**
- 고객: 이름, ID, PW, 전화번호, 생년월일, 고객번호
- 킥보드: ID, 브랜드, 연식, 기본료, 분당 가격, 회사
- 대여하다: 대여 상태, 대여 시간, 대여 위치

**관계**: 고객과 킥보드 사이의 '대여하다' 관계.

### 관계의 종류 (카디널리티)

- **1:1 관계**: 하나의 데이터가 다른 테이블의 하나의 데이터와 관계를 가짐. (예: 한 명의 고객은 하나의 계정만 가짐)
- **1:N 관계**: 하나의 데이터가 다른 테이블의 여러 데이터와 관계를 가짐. (예: 한 명의 고객은 여러 개의 주문을 할 수 있음)
- **N:M 관계**: 여러 데이터가 다른 테이블의 여러 데이터와 관계를 가짐. (예: 여러 고객이 여러 킥보드를 대여할 수 있음)

**N:M 관계**는 보통 중간에 새로운 테이블(개체)로 표기하며, 양쪽 개체의 기본키를 외래키로 가집니다.

### 관계 추가된 공유 킥보드 ERD (Peter Chen 방식)

- 고객과 '대여하다' 관계는 1:N (고객 한 명이 여러 번 대여할 수 있음).
- '대여하다'와 킥보드 관계는 N:1 (하나의 킥보드는 여러 번 대여될 수 있지만, 현재 대여는 한 번에 하나).

> 강의 자료상에는 고객과 대여하다 사이는 1:N, 대여하다와 킥보드 사이는 N:1로 표기되어 있으나, 요구사항에 '한 명의 고객은 한 번에 하나의 킥보드만 대여할 수 있습니다'라는 문구가 있어 실제 모델링에서는 다르게 해석될 수 있습니다.

### 🔍쉬운설명

**'ER 다이어그램'** 은 데이터베이스의 설계도를 그림으로 나타내는 방법입니다. 특히 **'Peter Chen' 표기법**은 데이터베이스의 기본적인 구성 요소인 개체, 속성, 관계를 시각적으로 쉽게 이해할 수 있도록 도와줍니다.

**ERD는 무엇인가요?**: 마치 가족 관계도를 그리는 것처럼, 우리 주변의 정보들(데이터)이 어떻게 서로 연결되어 있는지 그림으로 보여주는 것입니다. 예를 들어, '고객'과 '주문'이라는 정보가 있을 때, '고객이 주문한다'는 관계를 그림으로 나타내는 것이죠.

**Peter Chen 표기법의 주요 기호:**

- **개체 (네모)**: 데이터의 주인공입니다. '고객', '상품', '킥보드'처럼 실체가 있거나 개념적으로 중요한 것을 네모로 그립니다.
- **속성 (타원)**: 주인공의 특징들입니다. '고객'의 '이름', '주소', '전화번호' 같은 정보들을 타원으로 표현하고 개체에 연결합니다.
- **관계 (마름모)**: 주인공들 사이의 행동이나 연결고리입니다. '고객'이 '상품을 구매한다'와 같이 동사로 표현되는 관계를 마름모로 그립니다.
- **기본키 (밑줄 친 타원)**: 속성 중에서 주인공을 유일하게 구별할 수 있는 핵심 속성입니다. 예를 들어, '고객 ID'에 밑줄을 그어서 기본키임을 표시합니다.

**공유 킥보드 ERD 예시**: 만약 공유 킥보드 서비스를 만든다면, 이런 식으로 설계도를 그릴 수 있습니다.

- **고객 개체**: 네모 안에 '고객'이라고 쓰고, 타원들로 '이름', 'ID (기본키)', 'PW', '전화번호', '생년월일' 등의 속성을 연결합니다.
- **킥보드 개체**: 또 다른 네모 안에 '킥보드'라고 쓰고, 타원들로 'ID (기본키)', '브랜드', '연식', '기본료', '분당 가격', '회사' 등의 속성을 연결합니다.
- **대여하다 관계**: '고객'과 '킥보드' 사이에 마름모로 '대여하다'라는 관계를 넣습니다. 그리고 '대여하다' 관계에 '대여 상태', '대여 시간', '대여 위치'와 같은 속성을 연결할 수 있습니다.

**관계의 종류 (카디널리티)**: 두 개체 사이의 관계가 얼마나 많은지를 나타내는 숫자입니다.

- **1:1 관계**: '한 사람당 하나의 운전면허증'처럼, 왼쪽의 하나가 오른쪽의 하나와만 연결되는 경우.
- **1:N 관계**: '한 교수님이 여러 명의 학생을 가르친다'처럼, 왼쪽의 하나가 오른쪽의 여러 개와 연결되는 경우.
- **N:M 관계**: '여러 학생이 여러 과목을 수강한다'처럼, 왼쪽의 여러 개가 오른쪽의 여러 개와 연결되는 경우. 이 N:M 관계는 데이터베이스에서 직접 표현하기 어렵기 때문에, 중간에 '대여하다' 같은 새로운 개체를 만들어서 1:N, N:1 관계로 쪼개서 표현하는 것이 일반적입니다.

이러한 ERD를 통해 복잡한 시스템의 데이터 구조를 한눈에 파악하고, 개발자들이 서로 소통하며 데이터베이스를 효율적으로 설계할 수 있게 됩니다.

## ER 다이어그램 (IE)

**IE (Information Engineering) 표기법**은 Peter Chen 표기법보다 더 세부적으로 키(Key), 데이터 타입, 제약 조건을 표기하며 관계를 상세하게 나타냅니다.

### IE 표기법의 특징

- 개체를 **직사각형**으로 표현하고, 내부에 속성들을 나열합니다.
- 속성 옆에 `PK`(기본키), `FK`(외래키)를 명시하고, 데이터 타입(`INT`, `DATETIME` 등)과 `NOT NULL`, `VARCHAR(5)`, `UNIQUE` 같은 **제약 조건을 함께 표기**합니다.
- 관계는 선으로 연결하며, 관계의 종류(카디널리티 및 선택성)를 **'까마귀발(crow's foot)'** 기호를 사용하여 상세하게 나타냅니다.

### 까마귀발 (crow's foot) 표기법 기호와 의미

| 기호 | 의미 |
|:----:|:-----|
| `---O\|` | 0 또는 1 (선택적 하나) |
| `---\|\|` | 정확히 1 (필수 하나) |
| `---O<` | 0 이상 (선택적 다수) |
| `---\|<` | 1 이상 (필수 다수) |

ERD 그리기 도구: `app.diagrams.net`에서 IE 표기법으로 ERD를 그릴 수 있습니다.

### 공유 킥보드 ERD (IE 방식)

**`customer` 개체 (기본키)**

| 키 | 속성명 | 데이터 타입 및 제약 조건 |
|:--|:-------|:------------------------|
| PK | `customer_number` | `VARCHAR(10)` |
| | `name` | `VARCHAR(10) NOT NULL` |
| | `id` | `VARCHAR(15) NOT NULL UNIQUE` |
| | `pw` | `VARCHAR(20) NOT NULL` |
| | `phone_number` | `VARCHAR(11)` |
| | `birth_date` | `DATE` |

**`kickboard` 개체 (기본키)**

| 키 | 속성명 | 데이터 타입 및 제약 조건 |
|:--|:-------|:------------------------|
| PK | `id` | `VARCHAR(10)` |
| | `brand` | `VARCHAR(20) NOT NULL UNIQUE` |
| | `model_year` | `INT NOT NULL` |
| | `price_per_minute` | `INT NOT NULL` |
| | `basic_price` | `INT NOT NULL` |
| | `company` | `VARCHAR(20) NOT NULL UNIQUE` |

**`borrow` 개체 (고객과 킥보드 사이의 N:M 관계를 해소하는 연결 개체)**

| 키 | 속성명 | 데이터 타입 및 제약 조건 |
|:--|:-------|:------------------------|
| PK, FK | `customer_number` | `VARCHAR(10)` (고객을 참조하는 기본키이자 외래키) |
| PK, FK | `rental_time` | `DATETIME` (대여 시각을 나타내는 기본키이자 외래키) |
| FK | `id` | `VARCHAR(10)` (킥보드를 참조하는 외래키) ※강의 자료 그림에는 빠져있으나 `kickboard`의 `id`를 참조하는 FK가 추가되어야 함 |
| | `rental_status` | `ENUM('대여', '반납') NOT NULL` |
| | `rental_location` | `VARCHAR(20) NOT NULL` |

**관계:**
- `customer`와 `borrow` 사이: 고객 1명은 0회 이상(`---O<`) 대여 가능, 대여 기록은 반드시 1명의 고객에 속함(`---||`).
- `borrow`와 `kickboard` 사이: 킥보드 1대는 0회 이상(`---O<`) 대여될 수 있고, 대여 기록은 반드시 1대의 킥보드에 속함(`---||`).

### 🔍쉬운설명

**'IE 표기법'** 은 Peter Chen 표기법보다 더 자세하게 데이터베이스 설계도를 그리는 방법입니다. 마치 건축 설계도에서 '각 방의 크기는 몇 제곱미터이고, 창문은 어떤 유리로 만들며, 문은 어떤 재질이다'와 같이 **구체적인 정보들을 적어 놓는 것**과 비슷해요.

**더 자세한 정보 표시:**

- **직사각형 안에 키 정보 나열**: 개체는 커다란 직사각형으로 나타내고, 그 안에 모든 속성들을 쭉 나열합니다.
- **키와 데이터 타입 명시**: 각 속성 옆에는 이 속성이 기본키(`PK`)인지 외래키(`FK`)인지, 그리고 어떤 종류의 데이터(예: 문자열은 `VARCHAR(10)`, 숫자는 `INT`, 날짜는 `DATE`)인지, `NULL`을 허용하는지(`NOT NULL`), 중복될 수 없는지(`UNIQUE`) 같은 제약 조건까지 모두 적어줍니다. 이렇게 하면 나중에 실제 데이터베이스를 만들 때 훨씬 편리해요.

**까마귀발 (crow's foot) 표기법:**
관계의 선 끝에 '까마귀 발톱'처럼 생긴 기호들을 사용해서 두 개체 사이의 관계가 얼마나 많은지, 그리고 관계가 필수적인지 선택적인지 아주 상세하게 표현합니다.

- `---O|` (0 또는 1): '선택적으로 하나'라는 뜻입니다. 예를 들어, 한 남자(개체1)가 결혼을 할 수도 있고 안 할 수도 있지만, 한다면 배우자(개체2)는 한 명이라는 의미.
- `---||` (정확히 1): '반드시 하나'라는 뜻입니다. 예를 들어, 모든 주문 기록(개체1)은 반드시 한 명의 고객(개체2)에게서 발생했다는 의미.
- `---O<` (0 이상): '선택적으로 여러 개'라는 뜻입니다. 예를 들어, 한 고객(개체1)은 주문을 안 할 수도 있고, 여러 번 할 수도 있다는 의미.
- `---|<` (1 이상): '반드시 여러 개'라는 뜻입니다. 예를 들어, 어떤 부서(개체1)에는 반드시 한 명 이상의 직원(개체2)이 있어야 한다는 의미.

**공유 킥보드 ERD (IE 방식) 예시**: IE 표기법으로 공유 킥보드 시스템을 그리면, `customer`, `kickboard`, `borrow`(대여) 세 개의 직사각형 테이블이 생깁니다.

- `customer` 테이블에는 `customer_number`가 기본키(`PK`)이고 `VARCHAR(10)` 타입이며, `name`은 `NOT NULL`과 같은 상세 정보가 붙습니다.
- `kickboard` 테이블도 마찬가지로 `id`가 기본키이고 `VARCHAR(10)` 타입이며, `brand`는 `NOT NULL`과 `UNIQUE` 제약 조건이 붙습니다.
- `borrow` 테이블은 고객과 킥보드의 대여 관계를 기록하는 중간 테이블인데, 여기에 `customer_number`와 `rental_time`이 `PK`이자 `FK`로 지정되고, `rental_status`는 '대여' 또는 '반납' 중 하나만 가질 수 있는 `ENUM` 타입으로 정의됩니다.

관계 선을 보면 `customer`와 `borrow` 사이에는 `---O<`(0 이상)와 `---||`(정확히 1) 기호가 있는데, 이는 "한 고객은 대여를 안 할 수도 있고(0), 여러 번 대여할 수 있으며(이상), 하나의 대여 기록은 반드시 한 고객에게 속한다"는 의미입니다. 마찬가지로 `borrow`와 `kickboard` 사이의 관계도 해석할 수 있습니다.

IE 표기법은 이처럼 데이터베이스의 세부적인 구조와 제약 조건까지 명확하게 표현하여, **실제 데이터베이스 구현에 필요한 모든 정보를 제공**합니다.
